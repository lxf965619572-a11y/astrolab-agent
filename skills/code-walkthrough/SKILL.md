# 嵌入式 C 代码走查

## 输入和输出

- **输入**：被走查的源代码；需求规格说明（表 4-1 要对应需求章节号）；详细设计说明（专项检查对照附录C、单元的数据和中断设计）；目标平台；安全关键等级。
- **输出**：
  - 走查记录（工作底稿）`review/走查记录-<配置项简称>-<日期>.md`：工具告警甄别、逐函数走查、专项检查、问题清单、建议、待确认问题、统计。
  - 走查报告（部门模板 11）`review/<软件名称>（<版本>）走查报告.md`：由脚本从记录生成，含每个问题的软件问题报告单和走查建议列表。
- 格式见 [references/walkthrough-format.md](references/walkthrough-format.md)；编程规则见 [references/gjb8114-c.md](references/gjb8114-c.md)；部门嵌入式检查表见 [references/checklist.md](references/checklist.md)。

下文 `<脚本目录>` 指本 Skill 所在目录下的 `scripts`。

## 步骤

1. **确认范围。**要走查的文件或目录、目标平台（`sparc` 或 `d2000`）、安全关键等级、需求规格说明和详细设计说明在哪里。目标平台不明时先问用户，不要猜；没有需求和设计文档时可以走查，但表 4-1 的需求章节号和专项检查中依赖设计的部分写【待确认】，并告诉用户。
2. **运行工具。**
   - `mcp__cppcheck__run_cppcheck`：`target` 填目标平台，`includeDirs` 填头文件目录。结果保存在 `.cppcheck/last-run.json`。
   - `node <脚本目录>/gjb-scan.mjs <源码目录> --json review/gjb-scan.json --md review/gjb-scan.md`：GJB 8114 强制准则中能按词法判断的部分。
   - `mcp__utest__compile_check`（工具可用时）：严格告警编译，查类型转换、有无符号比较、返回值等编译器能发现的规则。
   - `node <脚本目录>/metrics.mjs <源码目录> --json review/metrics.json --md review/metrics.md`：文件、函数清单和代码行数（报告 3.2 的代码行数、逐函数走查的覆盖核对都用它）。
3. **逐条甄别告警。**打开每条告警对应的源码，读上下文，判定为违反、问题、误报或特殊设计，写进记录第 3 节，一条告警一行，不能只写问题。误报写明为什么不成立；特殊设计写明设计依据（详细设计条目号）和不影响功能的理由。需要规则说明时调用 `mcp__cppcheck__explain_check` 或查规则表。
4. **逐函数人工走查。**工具只能发现一部分问题。逐个文件、逐个函数（含 static）阅读，按规则表中标“人工”的条目和部门检查表 A～E 逐项检查；对照详细设计检查实现是否一致（处理流程、判断条件的 `>` 与 `>=`、返回值、全局变量的使用）。走查结果写进记录第 4 节，每个模块对应到需求规格说明章节号。不能因为工具没报就跳过。
5. **专项检查。**按 walkthrough-format.md 第 3 部分逐项检查代码，写进记录第 5 节 5.1～5.8：新状态复核、安全关键功能、数据访问冲突（填检查表）、数据有效性判断、单粒子防护、时序、时间系统、编程编译规范性。不涉及的写“不适用：<理由>”。
6. **写问题清单和建议。**问题写进第 6 节：文件:行号、函数、来源、检查项（规则编号或检查表编号）、问题描述、严重等级（Ⅰ～Ⅴ级，按 GJB 438B 的定义）、问题类别、具体的修改建议。只是改进建议的写进第 7 节。需要设计师或用户确认的写进第 8 节。最后填第 9 节统计。
7. **运行检查脚本（必须）。**

   ```
   node <脚本目录>/check-wt.mjs review/走查记录-<简称>-<日期>.md --root <代码根目录>
   ```

   脚本核对：每条告警都已甄别、违反和问题都有问题编号、问题清单的格式和等级、逐函数走查覆盖了全部文件和函数、专项检查不空、统计数字。“必须处理”全部改完；“复核”逐条判断。
8. **生成走查报告。**

   ```
   node <脚本目录>/gen-wt-report.mjs review/走查记录-<简称>-<日期>.md --out "review/<软件名称>（<版本>）走查报告.md"
   ```

   报告的表格、问题报告单、数字都来自记录，**不手改**；记录改了就重新生成（加 `--force`）。然后填写报告中的【待补充】（开发环境、引用文件的文档号等，有依据的填，没有的保留并告诉用户），按记录改写第 6 章测试总结（结论要与问题数一致：有未关闭的问题就不能写“通过”）。再运行一次检查脚本并加 `--report <报告路径>`。
9. **导出（用户要求时）。**`mcp__docgen__render_docx` 套 `部门-走查报告` 模板生成 Word，`fields` 用报告文首注释中给出的内容提要、主题词；编号、密级、编写、审核等不填，留给用户在 Word 中补。问题清单用 `mcp__docgen__export_xlsx`（`include: "问题清单"`）导出，加 `reviewColumns: ["开发人员反馈意见", "处理结果", "状态"]`。

## 约束

- **只读走查。**不修改被走查的源文件，修改建议写在记录里。
- **每个问题都能定位。**对应到具体文件、行号、规则或检查项，不写泛泛而谈的意见。
- **不照代码猜设计。**代码与设计不一致时，按设计判断；设计没有规定的，写进待确认问题，不自己裁决。
- **工具结果不能代替人工。**规则表中标“人工”的规则、检查表 C、D、E 类（中断、可靠性、平台相关）只能靠读代码。
- **等级就高不就低。**拿不准严重等级时取较高的一级，并在问题描述中写明影响。
