# 走查记录和走查报告格式

走查有两份输出：

| 文件 | 性质 | 位置 | 怎么写 |
|---|---|---|---|
| 走查记录 | 工作底稿：工具告警甄别、逐函数走查情况、专项检查、问题清单、建议、待确认问题 | `review/走查记录-<配置项简称>-<日期>.md` | 智能体按本文第 1 部分编写 |
| 走查报告 | 部门模板 11《软件走查报告》 | `review/<软件名称>（<版本>）走查报告.md` | `scripts/gen-wt-report.mjs` 从记录生成，再补【待补充】 |

报告中的表格、问题报告单、统计数字全部来自记录，不手改；要改就改记录再重新生成。

## 第 1 部分 走查记录

标题、章节号、表头照抄，脚本按它们读取。

### 各节写法

**第 3 节 工具告警甄别。**Cppcheck 的每条告警（编号 CK-nnn，按运行记录顺序）、gjb-scan 的每一处（沿用 GS-nnn）、compile_check 的每条告警（CC-nnn）都要有一行，不能只挑问题写。

- **判定**只写四种：`违反`（违反编程规则）、`问题`（不违反规则但是缺陷，如 Cppcheck 报的越界）、`误报`、`特殊设计`（违反规则但有设计上的理由，如主循环 `while (1)`）。
- **理由**：误报写清为什么不成立（“第 35 行两条路径都已赋值”）；特殊设计写清设计依据（详细设计条目号），并说明对功能、性能没有影响的理由。
- **对应问题**：判定为违反或问题的，写问题清单中的编号；同一原因的多条告警可以对应同一个问题。特殊设计、误报写“—”。
- 规则一栏写 GJB 8114 规则编号；Cppcheck 告警对应不到规则的写 Cppcheck 规则 ID。

**第 4 节 逐函数走查。**按模块（.c 文件或功能模块）和头文件分行，覆盖走查范围内的全部文件；“走查的函数”列出该模块的全部函数（含 static）。对应需求规格说明章节号写 SRS 章节号和需求标识；没有对应需求的写“无对应需求”并在说明中解释（工具函数、头文件写“通用定义”）。有问题的模块“是否通过审查”写“否”，说明中写问题编号。这一节生成报告的表 4-1。

**第 5 节 专项检查。**每一小节写：检查了什么（对象、依据）、怎么查的、结论（发现的问题写问题编号）。不涉及的写“不适用：<理由>”，不能空着。检查内容见第 3 部分。

**第 6 节 问题清单。**一个问题一行。

- **来源**：`人工`、`Cppcheck:<规则ID>`、`gjb-scan`、`编译`。工具发现并判定为违反/问题的，来源写工具。
- **检查项**：GJB 8114 规则编号（R-x-x-x）或走查检查表编号（A1～E4），或专项检查节号（5.3）。
- **严重等级**按 GJB 438B 的定义：

| 等级 | 含义 |
|---|---|
| Ⅰ级 | 妨碍完成关键功能，或危及人员、设备安全 |
| Ⅱ级 | 对关键功能有不利影响，且没有替代办法 |
| Ⅲ级 | 对关键功能有不利影响，但有替代办法 |
| Ⅳ级 | 不影响关键功能，给使用和维护带来不便（含违反编程规则但不影响功能的） |
| Ⅴ级 | 其他（不影响功能和使用的轻微问题） |

  拿不准的取较高等级，并在问题描述中说明影响。只是改进建议、不构成问题的，写进第 7 节，不在这里定级。
- **问题类别**：程序问题 / 文档问题 / 设计问题 / 其它问题。代码与设计不一致而代码是对的，是“文档问题”；设计本身有错是“设计问题”。
- **修改建议**：给出具体改法或 diff 片段，不写“建议修改”。

**第 9 节 统计。**数字由检查脚本核对。

## 第 2 部分 走查报告（部门模板 11）

由 `gen-wt-report.mjs` 生成，结构如下（章节号、表号照抄模板）。生成后智能体只做两件事：填【待补充】，改写叙述段落使之与记录一致。

```
封面字段（编号、密级……）在 Word 模板中，render_docx 时由用户补
内容提要：本文档为<软件名称>（<版本>）的走查报告，包括对走查工具、走查结果的描述，并对走查发现的问题进行说明及提出修改建议。
主题词：走查报告
1 范围
1.1 标识              ← 记录第 1 节
1.2 文档概述          ← 固定句式
1.3 软件开发环境      ← 记录第 1 节“开发环境”
1.4 软件运行环境      ← 记录第 1 节“运行环境”
2 引用文件            ← GJB 8114-2013、研制任务书、需求规格说明、详细设计说明
3 走查过程
3.1 走查工具          表3-1 走查工具表（走查工具名称 | 版本） ← 记录第 2 节
3.2 走查结果          表3-3 走查过程表（工作内容 | 输出结果 | 时间） ← 统计
4 走查结果说明
4.1 功能需求审查结果说明   表4-1 代码审查结果记录表 ← 记录第 4 节
4.2 专项检查结果
4.2.1 新状态复核结果 … 4.2.8 编程、编译规范性检查结果 ← 记录 5.1～5.8；4.2.3 含表4-2 数据访问冲突检查表
5 发现问题说明        ← 固定句式 + 问题和建议数量
6 测试总结            ← 统计和结论（智能体改写）
附录A 走查问题及建议
  软件问题报告单 <问题编号>（每个问题一张）
  走查建议列表
```

模板原文的勘误（已在生成的报告中改正）：引用文件“Q/W-Q-80-18-01A-2024 …（2014版）”按部门决定改为实际依据的 GJB 8114-2013；第 5 章“如附录1所示”改为“如附录A所示”；表号 3-1 之后是 3-3（模板原样保留）。

## 第 3 部分 专项检查内容

专项检查对照的是详细设计说明附录C“设计与实现阶段确认检查表”在**代码**中的落实。逐项看代码，不只看设计文档。

| 节 | 检查什么 | 怎么查 |
|---|---|---|
| 5.1 新状态复核 | 本版本相对上一版本（或相似产品）的新增、更改内容：新硬件、新接口、新功能、更改的需求 | 对照需求规格说明的更改记录（附录C）、详细设计附录B 的变更标识，逐项找到实现代码并检查；没有更改信息的写【待确认】并列入待确认问题 |
| 5.2 安全关键功能 | SRS 中带 -K 属性的需求和安全性需求（SREQ）的实现 | 列出每条安全关键需求的实现函数，检查输入检查、冗余（三取二、双份比对）、故障检测与处理、安全默认状态、参数和指令的合法性判断 |
| 5.3 数据访问冲突 | 中断与中断、中断与主程序（任务）共享的变量、缓冲区、外设寄存器 | 找出每个中断服务程序访问的全局变量和寄存器，与主程序的访问对照，填表；检查 volatile、关中断范围、多字节变量和结构体的原子性、读-改-写 |
| 5.4 数据有效性判断 | 外部输入数据（总线、串口、AD、遥控）的有效性判断 | 每个输入数据检查：来源、判断条件（范围、校验和、帧长、帧头、超时）、判断方法、判断结果的生存时间、无效时的处理，与详细设计各单元表 -2 一致 |
| 5.5 单粒子防护 | 软件防护措施的落实 | 关键数据三取二或冗余存储、定期刷新配置寄存器、EDAC 使能和错误处理、看门狗、程序跑飞防护（未用中断陷阱、未用存储区填充）、上电 RAM 清零（具备 EDAC 的 CPU 在清零前不读 RAM） |
| 5.6 时序 | 任务时序、中断时序、总线通讯时序、硬件操作时序 | 等待硬件的循环有超时；寄存器写入后需要的延时；BM3803 的 PSR、WIM、TBR、ASR16、ASR17 写操作后三条 NOP；中断服务程序执行时间；初始化顺序（先关中断，再初始化寄存器和全局变量，再初始化外围芯片，最后开中断）；沿触发中断初始化后清一次 |
| 5.7 时间系统 | 时间基准、守时、格式、校时；计数器初始化、计数条件、清零 | 32 位计数器回绕（用无符号差值比较）、计数器溢出和跳变的保护、校时的范围判断、时间单位换算；没有时间系统的写“不适用：本软件无时间系统” |
| 5.8 编程、编译规范性 | 编程规则执行情况、编译选项 | 汇总第 3 节 GJB 8114 违反情况（按规则统计）；compile_check 严格告警情况；编译器版本、优化级别、编译选项与详细设计 5.2 编程编译规范性的规定一致 |

涉及 1553B、CAN 的软件，再按详细设计附录C 专用要素第 6～20 项逐项检查代码，写在 5.4 或 5.6 中；不涉及的不写。
