# 插件创作

插件 = 技能 + 工具服务 + 模板，一起安装。工具服务是一个小程序，智能体通过它做自己做不准或做不了的事：按协议算 CRC、解析报文、检查寄存器配置表、调用部门的检查程序。**工具服务会在每个安装了插件的人电脑上运行，所以必须简单、只读为主、不联网，并且要经过审核。**

## 适用范围

- **工作区**：“我的库”。插件放在 `plugins/<插件名>/`，插件名用小写英文和连字符。
- **输出**：
  ```
  plugins/<插件名>/
    plugin.json            插件说明（格式见下）
    README.md              给人看：做什么、怎么用、工具列表、局限
    skills/<技能名>/SKILL.md 告诉智能体什么时候、怎么用这些工具（按 skill-authoring 技能的要求写）
    mcp/<服务名>/server.mjs 工具服务
    mcp/<服务名>/mcp-lite.mjs  从本技能的 assets/ 复制，不要改
    mcp/<服务名>/selftest.mjs  自测：直接调用工具函数，检查几组已知输入的输出
    templates/             需要时放模板
  ```
- **不做**：不写需要联网、需要安装 npm 包、需要管理员权限的工具；不调用 shell 执行用户给的命令；不删除文件。

## plugin.json

```json
{
  "name": "crc-tools",
  "title": "CRC 计算与核对",
  "version": "1.0.0",
  "description": "按部门通信协议计算 CRC-16/CCITT，核对报文里的 CRC 字段",
  "author": "<用户名>",
  "skills": ["skills"],
  "mcp": [{ "name": "crc", "command": "node", "args": ["mcp/crc/server.mjs"] }]
}
```

- `skills`：插件内技能所在的目录（一般就是 `skills`）。
- `mcp`：每个工具服务一项；`command` 写 `node`（工作台换成自带的 node），`args` 是相对插件目录的路径。智能体看到的工具名是 `mcp__<服务前缀>__<工具名>`，服务前缀 = `<插件名>_<服务名>` 转成小写、**连字符 `-` 全部换成下划线 `_`**、最长 32 个字符。例：插件 `info-flow-diagram`、服务 `infoflow` → `mcp__info_flow_diagram_infoflow__render_info_flow`。技能和 README 里写的工具名必须按这个规则换算，不要照抄插件名里的连字符。
- `version`：每次改动后提高（1.0.0 → 1.0.1 或 1.1.0），别人才能看到“有更新”。

## 步骤

1. **弄清要什么工具。**用 `ask_user_question` 问清：工具要算什么、查什么；输入（文件、十六进制串、参数）和输出；依据（协议文档、规范条款，让用户给文件）；几组已知正确的输入和结果（用来自测）。先用 `mcp__knowledge__search_knowledge` 查有没有现成的经验或代码。
2. **设计工具接口，给用户看。**每个工具：名字（小写英文加下划线，动词开头，如 `check_crc`）、一句话说明（做什么、什么时候用、返回什么）、参数（类型、单位、取值范围）。工具要小而准：一个工具做一件事，返回结构化结果和一句结论。用户同意后再写。
3. **写工具服务。**从 `assets/server-template.mjs` 开始，把 `assets/mcp-lite.mjs` 复制到同目录。要求：
   - 只用 Node 内置模块；不用 `child_process`，确需调用部门已有的检查程序时先问用户，并在 README 和 plugin.json 里写明。
   - 读写文件只在工作区（`process.cwd()`）里，用模板里的 `inWorkspace` 检查路径；默认只读。
   - 参数先校验，错误时抛出中文错误信息（说明哪里错、应该怎样）。
   - 算法照依据文档实现，在代码注释里写明依据（文档名、章节）。
   - 工具生成文件时，把生成它的输入（规格、参数）也存成一个文件放在旁边，这样以后改一处就能重新生成，不依赖当时的对话。
4. **写自测并运行。**`selftest.mjs` 直接 import 工具函数（把计算部分写成可导出的函数），用用户给的已知结果检查，运行 `node mcp/<服务名>/selftest.mjs` 全部通过。再用 stdio 试一次握手：`initialize`、`tools/list`、`tools/call` 各发一行 JSON，确认能返回。
5. **写插件里的技能。**按 `skill-authoring` 技能的要求（包括头信息里的 title、category、summary、keywords，发起页靠它们显示和推荐）：什么时候用这些工具、调用顺序、结果怎么用、不能用工具结果代替什么判断。
6. **写 README.md。**做什么、工具列表（名字、参数、返回）、依据、局限、版本记录。
7. **收尾。**告诉用户：在工作台“技能与插件 → 我做的”里点“试用”安装，引擎重启后智能体就能用；试用时新开一个任务，让智能体按技能真实调用一次工具，核对工具名、返回和生成的文件。试用没问题再“提交到共享库”（审核人会看全部代码）。不要自己提交 Git。
   - 自测、演示时生成的文件（图、报告）放进插件自己的 `skills/<技能>/tests/` 下当作期望结果，不要散落在库的根目录。

## 审核时会看的（自己先查一遍）

| 项 | 要求 |
|---|---|
| 依赖 | 只有 Node 内置模块和同目录的 mcp-lite.mjs |
| 网络 | 没有 `http`、`https`、`net`、`fetch` |
| 进程 | 没有 `child_process`（或已和用户确认并写明原因） |
| 文件 | 只在工作区里读写，路径经过检查；不删除文件 |
| 结果 | 自测通过；算法注明依据 |
| 说明 | plugin.json 字段齐全，README 写明工具和局限，版本号已更新 |
| 工具名 | 技能和 README 里的完整工具名按上面的规则换算（连字符换成下划线），和试用时智能体看到的一致 |
