# 航天嵌入式软件单元测试设计

## 适用范围

- **输入**：被测模块的源文件和头文件、详细设计（预期结果的依据，必需），需要时还有需求规格说明、接口控制文件。
- **输出**：测试代码（驱动、桩、用例），单元测试报告（用例表、运行结果、覆盖率、疑似缺陷、未覆盖项说明、MC/DC 分析、待确认问题）。
- **不做**：不修改被测代码，不修复缺陷。发现的问题写成疑似缺陷交给开发者处理。

## 步骤

1. **确认输入和范围。**以下事项不明确时先问用户：
   - 被测文件：哪些 `.c` 和 `.h`，被测函数是全部还是部分。
   - 设计依据：详细设计文件的名称和版本。**没有详细设计时，先问用户要；用户确认只能依据需求时，依据列写需求条目。不能只依据代码。**
   - 目标平台：SPARC（BM3803/3823/3883）等裸机代码，用手写驱动和桩（`framework: "c"`）；D2000 上运行操作系统的代码，用 gtest（`framework: "gtest"`，先读 [references/gtest-d2000.md](references/gtest-d2000.md)）。
   - 覆盖率要求：部门没有另外规定时，语句 100%，分支 100%，MC/DC 尽可能高；达不到的逐项说明原因。
   - 编译开关：被测代码需要的宏（如 `UNIT_TEST`、型号配置宏）。

   调用 `mcp__utest__toolchain_info` 查看本机编译器。没有编译器时告诉用户安装方法（见 README“单元测试”一节），用例设计和测试代码照样完成，报告注明“未运行”，不写覆盖率数值。

   读取设计文件：`.docx`、`.pdf` 用 `mcp__docreader__read_document`，先看 outline，再分段读完。
2. **分析被测单元。**逐个函数列出：
   - 设计规定的输入（参数、全局变量、寄存器、下层函数返回值）和输出（返回值、全局变量、寄存器写入、对下层函数的调用和参数）。
   - 设计规定的处理规则、检查顺序、边界、计数和状态变化。
   - 设计没有规定、或规定含糊的行为，列为待确认问题（Q-xxx）。
3. **读代码，只为确定结构。**读代码是为了知道函数原型、需要哪些桩、有哪些判定和条件（MC/DC 用）、static 函数和寄存器访问方式。**预期结果不从代码推导。**代码与设计不一致时，按设计写预期，测试失败后列为疑似缺陷。
4. **设计用例。**按 [references/test-design-methods.md](references/test-design-methods.md) 逐个函数设计：等价类、边界值、判定和条件（含 MC/DC）、错误处理和检查优先级、状态和计数（初值、回绕、饱和、复位）、字节和位处理。每个用例写明依据（设计文档的章节号）。依据只能写设计文件中真实存在的章节；设计未规定的写“设计未规定，见 Q-xxx”，这类用例只检查设计规定了的部分。
5. **编写驱动和桩。**按 [references/stub-driver-conventions.md](references/stub-driver-conventions.md) 编写，放在被测模块目录下的 `test/`；被测模块有多个单元（多个 `.c`）时，每个单元一个测试程序，放在 `test/<单元名>/`，其他单元用桩代替（约定第 1 节）。用例标识按 [references/test-case-format.md](references/test-case-format.md) 的规则编写，与报告用例表一一对应。
6. **运行并处理结果。**调用 `mcp__utest__run_unit_tests`（`sources` 只列被测 `.c`，`tests` 列驱动和桩）。按结果处理：
   - **编译或链接失败**：缺函数就补桩，重复定义按工具提示处理。不改被测代码。
   - **用例失败**：先检查用例本身：输入是否按设计组织，预期是否按设计推导，算术是否算对。用例确实写错了（预期与设计不符），改正用例，并写入报告的“用例修正记录”，注明修正前、修正后和设计依据。用例没错，就是**疑似缺陷**：保留这个失败的用例，不改预期，写入疑似缺陷表。
   - **覆盖率未达标**：用 `mcp__utest__coverage_detail` 查看未覆盖的行和分支，按设计补充用例。仍然覆盖不到的，在“未覆盖项说明”中逐行写原因（见 test-case-format.md）。“来不及”“后续补充”不是原因。
   - **崩溃或超时**：工具会给出最后开始的用例。等待循环用桩控制退出；空指针、越界属于疑似缺陷。
   - **MC/DC**：编译器支持（GCC 14 及以上）时，工具直接给出 MC/DC 覆盖率。不支持时，对每个含两个及以上条件的判定写 MC/DC 分析表，用 `mcp__utest__check_mcdc` 核对；没有满足的条件，按工具建议的向量补用例，补不出的说明原因。

   改动测试后重新运行，直到用例和覆盖率的状态稳定。**报告必须以最后一次运行的结果为准。**
7. **写报告。**按 [references/test-case-format.md](references/test-case-format.md) 编写单元测试报告，保存为被测模块目录下的 `test/单元测试报告-<模块名>-<日期>.md`（多个单元时每个单元一份，放在 `test/<单元名>/`）。运行结果、覆盖率直接取自最后一次运行，不自己计算或估计。
8. **运行检查脚本（必须）。**

   ```
   node <本 Skill 所在目录>/scripts/check-ut.mjs <报告路径> --run <运行记录路径>
   ```

   运行记录路径就是 `run_unit_tests` 结果最后一行的“运行记录”。脚本核对用例标识、预期依据、失败用例、未覆盖项、统计数字和 MC/DC 写法。“必须处理”项逐条改正，“复核”项逐条判断，保留的在回复中说明理由。改完再运行一次，直到没有“必须处理”项。最后把脚本的统计行告诉用户。
9. **导出（用户要求时）。**用 `mcp__docgen__export_xlsx` 把用例表、疑似缺陷表、待确认问题导出为 `.xlsx`。疑似缺陷表加 `reviewColumns: ["开发者意见", "处理结果", "状态"]`。部门有单元测试报告模板时，先用 `mcp__docgen__list_templates` 查看，再用 `render_docx` 生成；没有对应模板时只导出 `.xlsx`，并告诉用户。

## 约束

- **不修改被测代码。**被测的 `.c` 和 `.h` 一个字符都不改，包括临时加打印、去掉 `static`、改宏、改等待循环。需要时用桩、编译宏、替换头文件、在测试文件中 `#include` 被测 `.c` 等方法（见 stub-driver-conventions.md）。工具会核对运行前后被测文件是否变化。
- **预期结果来自设计。**不能先运行再把实际输出抄成预期。预期值要按设计手算，或在测试代码中用独立的方法计算，不能调用被测函数计算预期（如用被测的校验和函数算预期校验和）。
- **不为通过而改预期。**用例失败时，只有证明用例本身与设计不符才能改，并记入用例修正记录。不删除失败的用例，不把失败用例改成只检查“不崩溃”。
- **不编造依据。**依据列只写设计文件中存在的章节号。不写“按编码规范”“按部门规定”这类输入中没有的依据。
- **不夸大覆盖率。**覆盖率只写工具给出的数值。编译器不能测量 MC/DC 时，写“MC/DC：未测量；分析表核对 N 个判定，满足 M 个”，不写百分比。用例没有运行就写“未运行”。
- **说明主机测试的局限。**主机（x86，小端）与目标机（SPARC 大端，D2000 为 ARM）在字节序、`char` 符号、`long` 和指针宽度、对齐、寄存器和中断时序上不同。报告中列出需要在目标机或真实硬件上验证的项。
- **不在外网处理真实型号代码。**使用云端模型时只处理样例或脱敏代码。
- **部门规定优先。**部门有单元测试规范、报告模板、用例标识规则时，以部门规定为准。

## 常见错误做法

| 不应这样做 | 问题 | 应这样做 |
|---|---|---|
| 运行后发现温度门限 1000 返回 `CMD_ERR_PARAM`，把预期改成 `CMD_ERR_PARAM` | 把代码行为当预期，缺陷被掩盖 | 设计规定 0～1000 合法，保留预期 `CMD_OK`，列为疑似缺陷 |
| 在被测 `.c` 中去掉 `static`，以便测试调用 | 修改了被测代码 | 测试文件中 `#include` 被测 `.c` |
| 调用被测的 `cmd_checksum()` 计算帧的预期校验和 | 预期依赖被测代码，缺陷会同时出现在预期和实际中 | 在测试代码中逐字节相加，或写手算的常量 |
| 把“1000 判非法”写成“边界值测试通过，代码按 ≥1000 判非法” | 用代码解释设计 | 依据写设计章节，结论写“与设计不符，见 DEF-001” |
| 未覆盖的分支写“防御性代码，不可达”，实际构造参数就能到达 | 以不可达为由放弃覆盖 | 先尝试构造输入；只有说明了为什么任何输入都到不了，才能写不可达 |
| 为避免超时，修改被测代码中的等待循环 | 修改了被测代码 | 用桩函数或寄存器替换宏，在第 N 次读取后改变状态 |
| 编译器不支持 MC/DC，报告写“MC/DC 覆盖率 100%” | 夸大 | 写分析表核对结论，注明未测量 |
| 设计没有规定空指针时的返回值，按代码写预期 `-1` | 设计未规定的行为被当成已规定 | 列 Q-xxx；用例只检查不崩溃、不修改输出 |
| 设计写明“len 等于 8”，用例失败后又列待确认问题“是否允许大于 8”，缺陷建议写“或修改设计” | 设计已有明确规定，却为代码的行为找理由 | 设计明确的直接按设计判为疑似缺陷，建议只写代码怎么改；只有设计确实没写或写得含糊才列待确认问题 |
