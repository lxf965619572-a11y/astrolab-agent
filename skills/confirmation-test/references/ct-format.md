# 确认测试记录和确认测试报告格式

| 文件 | 性质 | 位置 | 谁写 |
|---|---|---|---|
| 确认测试记录 | 工作底稿：测试环境、测试要点、测试项目、用例（设计和执行结果）、不可测试项、问题报告单、待确认问题、统计 | `test/确认测试记录-<配置项简称>-<版本>.md` | 智能体设计用例；实际结果只能由 `ct-results.mjs --import` 从测试人员填好的执行记录表导入 |
| 执行记录表 | 给测试人员在测试现场填写的表（每个步骤一行） | `test/确认测试执行记录表-<简称>-<版本>.md` / `.xlsx` | `ct-results.mjs --export` 生成，测试人员填写 |
| 确认测试报告 | 部门模板 05《XX软件确认测试报告》 | `test/<软件名称>（<版本>）确认测试报告.md` | `gen-ct-report.mjs` 从记录和需求规格说明生成，再补【待补充】 |

### 写法

**用例标识**：`<测试项目标识>-<三位序号>`，测试项目标识为 `<软件简称>-<测试类型英文>-<功能简称>`（模板示例 `XX-Interface-XX-001`）。测试类型英文：Function（功能）、Interface（接口）、Performance（性能）、Boundary（边界）、Robust（健壮性）、Stress（强度）、Safety（安全性）、KeySafety（安全关键功能专项）、Recovery（恢复）。

**功能项**：只写需求规格说明附录B.1 中真实存在的需求标识，可写多个。**每条需求至少有一个用例覆盖，或列入第 7 节不可测试项并写明原因和在什么时机验证**（代码走查、单元测试、分系统测试等）。设计约束、编程编译要求这类 RREQ 一般列为不可测试项，测试时机写“静态分析、代码走查”。

**期望结果**：写可观察、可判定的结果（遥测量的具体值或变化、输出波形、计数增量、时间上限），数值有依据（需求规格说明、通信协议的章节号写在“依据”里）。不写“正常”“正确”“符合要求”这类无法判定的词。需求没给数值的，写进第 9 节待确认问题，不要自己定。

**测试要点**：需求规格说明 7.4 表7.4-1 的每一条都要有编号（TP-序号）、有用例，或在“对应需求”写“不可测试（见 NT-xx）”/“本次未测试：<原因>”。交办方另给了测试要点的，用交办方的编号。

**健壮性用例**：按部门模板 3.2 的要求逐项考虑，没有对应功能的写进第 9 节说明不适用：
1. 星上采集数据的剔野测试（超出剔野限，误差范围一般在量程 10% 以内）；
2. 星上采集数据的限幅测试（超出限幅范围）；
3. 注入数据测试（超出最大长度、格式非法）；
4. 强度测试（长时间模飞运行，乱序指令、当前模式不支持的指令、频繁复位、切机、高频通讯等非常规操作；加大中断频率，验证可能存在数据访问冲突的工况）；
5. 部件故障（无数据、数据无效、数据超差）及其持续时间；
6. 部件切换后实际使用的数据源正确性；
7. 重要数据保存与恢复（各模式恢复正确性，恢复不成功后的工况）；
8. 通讯有效性（输入文件要求的所有状态字，如帧头、累加和、自检状态的正常和异常）。

**安全关键功能**：需求标识带 `-K` 的需求，每条至少一个专项用例（测试类型含“安全性测试”或用 KeySafety 项目），并从用户角度覆盖输入域、相关功能、相关变量的组合。

**执行结果**：实际结果、测试结论、执行人、执行日期、复核人、复核日期只能由 `ct-results.mjs --import` 写入（它同时填写第 1 节“执行记录来源”）。测试结论只能是 `通过`、`不通过`、`未执行`；不通过的必须有问题报告单编号；未执行的在备注写原因。

**问题报告单**（附录D）：问题编号 `<型号>-<版本>BUG-<三位序号>`（如 `TCUS-V1.00BUG-001`）。严重等级按 QJA 300-2014：致命问题 / 严重问题 / 一般问题 / 轻微问题 / 改进建议。问题类别（必选）：文档问题 / 设计问题 / 程序问题 / 其他问题；问题子类别可选（如“需求规格说明描述问题”）。处理方式：`下一版本更改` / `经认可不更改` / `待定`（决定报告结论用）。问题报告单由测试人员确认后填写；智能体可以起草现象描述和问题分析，但严重等级、处理方式、软件经理批复由人定。

## 第 2 部分 确认测试报告（部门模板 05）

`gen-ct-report.mjs` 生成，结构照抄模板（括号中是数据来源）：

```
内容提要 / 主题词（文首注释中给出 render_docx 的 fields）
1 引言：1.1 文档概述（固定句式 + 用例标识规则）；1.2 软件配置项基本信息（记录第 1 节）；1.3 缩略语定义【待补充】

3 测试概要
  3.1 测试环境及工具（表3.1-1，记录第 2 节）
  3.2 测试说明（用例来源、覆盖率、安全关键功能专项、强度测试、健壮性用例统计；智能体按实际改写）
  3.3 测试用例统计（表3.3-1：每个测试项目的执行用例数量、未通过数量、总计）

  3.6 安全关键功能（表3.6-1）
4 测试总结：4.1 测试结果分析（覆盖率、执行和通过数、问题数）；4.2 测试结论（按规则选四种情况之一）
附录A 软件确认测试工作准备状态检查表（按测试环境类型选半物理仿真或软平台表，检查结果由人填）

附录F《软件确认测试报告》-确认测试阶段确认检查表（19 项照抄，对应章节按本报告）
```

**测试结论规则（4.2）**：
- 全部用例执行且通过、没有问题报告单 → 情况（一）“本次测试没有发现软件问题，本次测试通过。”
- 不通过率（不通过用例数 ÷ 已执行用例数）超过 20%，或有“致命问题” → 情况（四）“测试异常终止”。
- 有问题且处理方式都已确定（下一版本更改 / 经认可不更改）→ 情况（二），写明各多少个。
- 有问题且有“待定”的 → 写【待补充】，由项目组讨论决定情况（二）或（三），不由智能体决定。
- 有未执行的用例 → 不能写“通过”，在 4.1 说明原因。

模板勘误（生成时已改）：3.4 的表号模板写作“表3.5-1”、3.5 写作“表3.6-1”、3.6 写作“表3.7-1”，按所在节改为表3.4-1、表3.5-1、表3.6-1；3.2 例句中“在3.5节，对测试要点进行跟踪”应为 3.4 节；附录F 第 3 项“第3.7节”应为第 3.6 节。
