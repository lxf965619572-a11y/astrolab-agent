# 航天嵌入式软件确认测试

确认测试在目标机、半物理仿真或软平台上由测试人员执行，**智能体不执行测试，也不填写实际结果**。智能体做三件事：设计用例；生成执行记录表；导入执行结果后生成报告并检查。

## 输入和输出

- **输入**：软件需求规格说明（部门模板 01 的 Markdown，有附录B.1 需求跟踪矩阵和 7.4 测试要点；Word 版先用 `mcp__docreader__read_document` 读）；任务书、通信协议（期望结果的数值依据）；测试环境说明（半物理仿真或软平台、设备清单）；回归测试时的更动影响域分析。
- **输出**：
  - 确认测试记录 `test/确认测试记录-<简称>-<版本>.md`（用例设计和执行结果都在这里）；
  - 执行记录表 `test/确认测试执行记录表-<简称>-<版本>.md` 和 `.xlsx`（给测试人员）；
  - 确认测试报告 `test/<软件名称>（<版本>）确认测试报告.md`（部门模板 05）。
- 格式见 [references/ct-format.md](references/ct-format.md)。

下文 `<脚本目录>` 指本 Skill 的 `scripts`。

## 第一阶段：设计用例

1. **确认输入。**需求规格说明的路径和版本、被测版本、测试环境类型（半物理仿真 / 软平台）和设备清单、是否回归测试。需求规格说明没有附录B.1 或 7.4 时告诉用户，需求清单会不全。
2. **列测试要点和测试项目。**测试要点取需求规格说明 7.4（交办方另给的测试要点也要列），编号 TP-xx。按功能划分测试项目（一个测试项目对应一组相关需求），定测试项目标识。
3. **逐条需求设计用例。**按 ct-format.md 第 1 部分的格式写进记录第 6 节：
   - 每条需求（附录B.1 中的每个标识）至少一个用例；性能需求写测量方法和判定上限。
   - 期望结果可观察、可判定，数值来自需求规格说明或协议，在“依据”中写章节号。需求没有给出数值的列为待确认问题，不自己定。
   - 带 `-K` 的安全关键需求做专项用例：输入域边界、相关功能组合、异常和恢复。
   - 健壮性用例逐项考虑部门模板的 8 类（剔野、限幅、注入数据、强度、部件故障、部件切换、数据保存与恢复、通讯有效性），不适用的在第 9 节说明。
   - 回归测试：按更动影响域分析，覆盖更动部分和受影响部分，并回归安全关键功能。
4. **列不可测试项。**测试环境做不到的（单粒子翻转、硬件故障、设计约束和编程要求等）写进第 7 节，写清原因和在什么时机、用什么方式验证。
5. **运行检查脚本（必须）。**

   ```
   node <脚本目录>/ct-results.mjs --stats test/确认测试记录-<简称>-<版本>.md
   node <脚本目录>/check-ct.mjs test/确认测试记录-<简称>-<版本>.md
   ```

   核对每条需求、测试要点、安全关键需求都有用例或不可测试项，用例可判定。“必须处理”全部改完。
6. **导出执行记录表。**

   ```
   node <脚本目录>/ct-results.mjs --export test/确认测试记录-<简称>-<版本>.md --out test/确认测试执行记录表-<简称>-<版本>.md
   ```

   再用 `mcp__docgen__export_xlsx`（`include: "执行记录"`）转成 Excel，告诉用户交给测试人员填写实际结果、测试结论、问题报告单编号、执行人和日期。用例设计要经测试经理确认，设计人一栏不要写成测试人员的名字。

## 第二阶段：执行后出报告

7. **导入执行结果。**测试人员填好的 Excel 用 `mcp__docreader__read_document` 读出，**原样**保存为 `.md`（不改任何内容），然后：

   ```
   node <脚本目录>/ct-results.mjs --import test/确认测试记录-<简称>-<版本>.md --from <填好的表.md>
   ```

   脚本只写实际结果、结论、执行人等，并记录来源，同时更新统计。脚本报告对不上的行时，问用户，不要猜。
8. **起草问题报告单。**对不通过的用例，在第 8 节起草现象描述和问题分析（引用实际结果和需求原文）；严重等级、问题类别、处理方式、软件经理批复由测试人员和软件经理确定，没给的写【待补充】并告诉用户。
9. **生成报告。**

   ```
   node <脚本目录>/gen-ct-report.mjs test/确认测试记录-<简称>-<版本>.md --out "test/<软件名称>（<版本>）确认测试报告.md"
   ```

   报告的表格、统计、附录B 用例记录、跟踪矩阵和 4.2 结论的选择都由脚本按规则生成，**不手改**；记录改了就重新生成（加 `--force`）。然后补【待补充】（1.3 缩略语、2.1 规范性引用文件、2.2 文件编号、3.2 中强度测试和数据访问冲突的验证情况、附录C 仿真曲线等），附录A 的检查结果由测试人员填。
10. **再检查一次。**`node <脚本目录>/check-ct.mjs <记录> --report <报告>`。
11. **导出（用户要求时）。**`mcp__docgen__render_docx` 套 `部门-确认测试报告` 模板生成 Word，`fields` 用报告文首注释中给出的内容提要、主题词；编号、密级、编写、审核等不填。跟踪矩阵可用 `mcp__docgen__export_xlsx` 导出。

## 约束

- **不编造执行结果。**实际结果、测试结论、执行人、执行日期只能从测试人员的执行记录导入。没有执行记录时报告停在设计状态，4.2 写【待补充】。
- **期望结果有依据。**数值来自需求规格说明、协议或任务书，写明章节号；没有依据的列为待确认问题。
- **全覆盖。**每条需求、每个测试要点、每个安全关键需求都要有用例，或列为不可测试项并写清验证时机和方式。
- **结论按规则。**未通过率超过 20% 或有致命问题时为“测试异常终止”；有待定的问题时由项目组决定通过或不通过，智能体不替项目组下结论；有未执行用例时不能写“通过”。
