# 航天嵌入式软件编码

## 适用范围

- **输入**：详细设计（必需，实现的依据），相关头文件和接口文件，已有代码（修改时），目标平台和编译器要求。
- **输出**：源文件和头文件；编码说明（实现清单与设计追溯、与设计的偏离和待确认问题、编译结果、静态检查结果、自查结果）。
- **不做**：不改设计文档；不写单元测试（单元测试环节做）；不改与任务无关的文件。

## 步骤

1. **确认输入。**以下事项不明确时先用 `ask_user_question` 问，不要猜：
   - 设计依据：详细设计的文件名和版本、本次实现哪些函数或哪一节。**没有详细设计时先要设计；用户确认没有设计时，先和用户一起把函数原型、输入输出、处理步骤和异常处理写清楚，记入编码说明，再写代码。**
   - 目标平台：`sparc`（裸机，大端，32 位）还是 `d2000`（Linux，小端，64 位）。决定字节序、类型长度、能否用操作系统接口。
   - C 标准：部门或项目规定 C89 还是 C99（默认 C99）；编译器和编译开关（项目已有 Makefile 时以它为准）。
   - 修改已有代码时：改哪些地方、原因（设计变更单号、问题报告号）。

   读设计：`.docx`、`.pdf` 用 `mcp__docreader__read_document`，先看 outline，再分段读完。

2. **列实现清单。**逐个函数（含 static）列出：原型、设计条目号、输入输出、处理步骤、异常处理、用到的全局数据和寄存器、是否在中断里调用。设计没写清、或与头文件、接口文件矛盾的地方，列为待确认问题（Q-xxx），涉及接口和行为的先问用户再写。

3. **读已有代码，保持一致。**看同一模块的命名、注释格式、错误码、寄存器访问方式、临界区写法，新代码照着写。修改时只改要改的地方，不顺手重排格式、改名或"优化"无关代码。

4. **写代码。**按 [references/coding-rules.md](references/coding-rules.md) 编写，文件头和函数头按 [references/comment-template.md](references/comment-template.md)。每个函数的函数头写明对应的设计条目号。设计里的处理步骤、检查顺序、边界、返回值一条都不能少，也不加设计没有的行为；觉得设计有问题时，按设计实现并写进待确认问题，不自行改变行为。

5. **编译检查（必须）。**调用 `mcp__utest__compile_check`（`target` 填目标平台，`std` 按项目规定，`includeDirs` 填头文件目录）。要求 0 个错误；每条告警都要处理：改代码消除，或在编码说明中写明保留理由（例如寄存器地址强制转换引起的 `-Wcast-align`，并说明地址已对齐）。工具说明用了主机 gcc 时，字节序、对齐、类型长度相关的代码要在第 7 步逐条人工确认。

6. **静态检查（必须）。**调用 `mcp__cppcheck__run_cppcheck`（`target` 同上）。逐条打开告警对应的代码判断：真实问题就改，误报写明理由，不确定的标"待确认"。需要规则说明时用 `mcp__cppcheck__explain_check`。改完重新运行第 5、6 步，直到结果稳定。

7. **自查（必须）。**
   - 运行检查脚本：`node <本 Skill 所在目录>/scripts/check-code.mjs <改过的 .c 和 .h 文件>`。脚本检查函数头注释和设计追溯、动态内存、递归调用、goto、`switch` 缺 `default`、没有超时的等待循环、魔数等。"必须处理"项逐条改正；"复核"项逐条判断，保留的写理由。
   - 按代码走查检查表（`code-walkthrough` 技能的 `references/checklist.md`）逐项对照自己写的代码，重点是中断与并发（C 类）、控制流与可靠性（D 类）、平台相关（E 类），这些编译器和 Cppcheck 发现不了。

8. **写编码说明。**保存为代码所在模块目录下的 `doc/编码说明-<模块名>-<日期>.md`（没有 `doc/` 时放在模块目录下），内容：
   - 实现清单：函数、设计条目号、文件:行号、状态（新增 / 修改 / 未改）。
   - 与设计的偏离和待确认问题（Q-xxx）：没有就写"无"。
   - 编译结果：编译器、标准、错误数和告警数，保留的告警及理由（照抄 `compile_check` 的结果，不自己估计）。
   - 静态检查结果：告警总数、真实问题已修改数、误报数及理由。
   - 自查结果：检查脚本的统计行；检查表中需要在目标机或真实硬件上验证的项。
   最后在回复里简要说明改了哪些文件、还有哪些待确认问题。

## 约束

- **以设计为准。**代码行为只来自设计；设计没写的行为不发明，列待确认问题。
- **不改设计、不改测试。**设计有错写进待确认问题，由设计人员改；不为让测试通过而改测试。
- **只改该改的。**修改已有代码时，改动范围限于任务；保留原有风格和注释。
- **结果不编造。**编译和静态检查的数字只写工具给出的。工具没有运行就写"未运行"。
- **说明主机检查的局限。**用主机 gcc 检查时，字节序、`char` 符号、`long` 和指针宽度、对齐、寄存器时序在目标机上可能不同，编码说明中列出需要在目标机上验证的地方。
- **不在外网处理真实型号代码。**使用云端模型时只处理样例或脱敏代码。
- **部门规定优先。**部门编码规范、注释模板与本技能不同时，以部门规定为准。

## 常见错误做法

| 不应这样做 | 问题 | 应这样做 |
|---|---|---|
| 设计写"连续 3 次校验失败置故障"，代码写成累计 3 次 | 改变了设计规定的行为 | 按"连续"实现：成功时清零计数；觉得应改为累计的，列待确认问题 |
| 设计没写空指针怎么办，代码返回 `-1` | 发明了设计没有的接口行为 | 列 Q-xxx 问设计人员；临时按部门惯例处理的，在编码说明中写明 |
| 等待硬件就绪写 `while ((REG & READY) == 0) {}` | 硬件故障时死循环 | 按设计的超时时间计数退出并返回超时错误码；设计没写超时的，列待确认问题 |
| 报文字段直接 `*(uint16_t *)&buf[3]` | SPARC 上非对齐访问陷阱，且依赖主机字节序 | 按字节移位组装，显式处理大端 |
| 中断和主程序共享的计数器没有 `volatile`，主程序读写不关中断 | 编译器优化和读写竞争 | 声明 `volatile`，多字节或读改写时按模块惯例进入临界区 |
| 为消除 `-Wconversion` 告警到处加强制转换 | 掩盖截断 | 先确认取值范围，选对类型；确实需要转换的，在转换处注释范围依据 |
| 顺手把整个文件的缩进和命名改成自己的风格 | 审核和追溯困难 | 只改任务需要改的代码 |
