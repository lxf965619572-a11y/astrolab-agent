# 需求条目质量规则

每条需求都要逐条过一遍以下规则。不满足时，能直接改写的就改写；需要用户或上级提供信息的，列入待确认问题，并注明违反的规则编号。

## 规则

| 编号 | 规则 | 判断方法 |
|---|---|---|
| Q1 | **完整**：有触发条件、输入、处理、输出、量化指标，以及异常情况的处理 | 问：什么时候做？拿什么做？做成什么样？做不成怎么办？ |
| Q2 | **无歧义**：只有一种理解方式 | 查下方模糊词表；查指代不清（“该数据”“上述参数”）；查“和/或”“等” |
| Q3 | **可验证**：能设计出判定通过或不通过的测试、演示、分析或审查 | 数值带单位和容差；写清测量起止点和测量条件 |
| Q4 | **一致**：与其他需求、其他章节、其他输入文件不冲突 | 同一参数在各处的数值、单位一致；术语一致；容量与时间核算闭合 |
| Q5 | **可追踪**：有唯一标识，有来源条款或派生理由 | 反向追溯表中没有空格 |
| Q6 | **单一**：一条需求只规定一件事 | 只有一个“应”；出现“并且”“同时”“以及”时考虑拆分 |
| Q7 | **可行**：在规定的硬件、接口速率和时序下能实现 | 做量级核算，如帧传输时间、CPU 负荷、存储容量 |
| Q8 | **不含设计**：写“做什么”，不写“怎么做” | 出现函数名、数据结构、具体算法实现时，确认是否为任务书规定的设计约束 |

## 模糊词表

出现以下词语时，要么替换为量化描述，要么列为待确认问题：

尽快、及时、迅速、快速、实时（未给数值时）、适当、合理、必要时、视情况、一般、通常、尽量、尽可能、足够、较高、较低、不宜过高、充分、正常情况下、友好、灵活、等、支持（未说明支持到什么程度）、具备……能力（未说明具体内容）。

## 改写示例

| 原文 | 问题 | 改写或处理 |
|---|---|---|
| 软件上电后应尽快完成初始化。 | Q2、Q3：“尽快”不可验证 | 软件应在上电后 【待确认】 ms 内完成初始化，并开始响应遥测请求。列为待确认问题，向总体确认时间指标 |
| 对非法指令应进行适当处理。 | Q1、Q2：未说明什么是非法、怎么处理 | 拆成三条：非法指令的判据（指令码不在码表中、校验错误、当前模式不允许）；处理方式（丢弃、不执行）；上报方式（错误计数加 1，下一帧遥测反映）。判据和上报方式没有来源时列为待确认问题 |
| 遥测帧采用累加和校验。 | Q1、Q4：未说明位宽、计算范围 | 软件应对遥测帧中从 【待确认】 到 【待确认】 的字节按字节累加，取低 16 位作为校验和。计算范围列为待确认问题 |
| CPU 负荷不宜过高。 | Q3 | 软件在最大负载工况下的 CPU 负荷应不大于 【待确认】 %。列为待确认问题 |
| 软件应采集模拟量并组帧下传，同时监视通信状态。 | Q6：一条规定了三件事 | 拆成三条需求 |

## 量级核算示例

- **帧传输时间**：异步串口每字节的位数 = 起始位 + 数据位 + 校验位 + 停止位，按接口要求实际计算。以 1 位起始位、8 位数据位、无校验、1 位停止位为例，每字节 10 位；有奇偶校验时为 11 位。115200 bps 下每字节约 86.8 μs，100 字节的帧约 8.7 ms。如果规定的应答时间是 10 ms，且从收到请求的最后一个字节算到发送完应答帧的最后一个字节，余量只有约 1.3 ms，应作为可行性风险提出。
- **数据区容量**：把遥测参数表中每个参数占用的字节数逐项相加，再与帧格式规定的数据区长度比较。超出时属于 Q4 和 Q7 问题。
