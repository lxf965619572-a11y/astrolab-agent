# 航天嵌入式软件需求分析

## 适用范围

- **输入**：软件研制任务书（或技术要求、任务分解）、接口控制文件（ICD）、单机或硬件说明、上级系统需求等。
- **输出**（两份，同时写，见 [references/output-format.md](references/output-format.md)）：
  - 《软件需求规格说明》：正式文档，**严格按部门模板**，结构见 [references/srs-structure.md](references/srs-structure.md)。
  - 《需求分析记录》：工作底稿，记录上级条款原文、覆盖分析、派生理由、待确认问题、检查表结论和统计，评审时对照用。
- **不做**：概要设计和详细设计。模块内部结构、函数划分、数据结构留到设计阶段。

产出是规格说明的初稿，必须由责任人确认，并按部门过程评审。

## 步骤

1. **确认输入和范围。**列出所有输入文件（名称、编号、版本、日期）。确认以下事项，不明确时先问用户，不要猜：
   - 型号简称 XX 和配置项简称 YY（用于需求标识 `XXYY-FREQnnn` 等）、软件名称和代号
   - 目标平台：SPARC（BM3803/3823/3883）或 D2000
   - 软件研制类型（I～IV 类）、安全关键等级（A～D 级）、继承基线（没有就是新研）

   任务书引用了但没有提供的文件（如 ICD、指令码表、遥测参数表、系统软件接口说明），记为待确认问题并告诉用户，不要凭经验补全。

   **读取输入文件**：`.docx`、`.xlsx`、`.pdf` 用 `mcp__docreader__read_document` 读取，不要用命令行解析二进制文件。长文档先用 `mode: "outline"` 看章节结构，再按 `nextOffset` 分段读完，不能只读开头。返回结果中的“注意”事项要在分析中考虑：图片里的框图、时序图没有被读出，相关内容列为待确认问题，请用户补充；合并单元格已经展开，核对表格时注意。旧版 `.doc`、`.wps` 读不了，请用户另存为 `.docx`。
2. **逐条摘录上级条款**，写入分析记录第 2 章。把每份输入中含“应、须、要求、不得、不大于、不小于”的语句，以及表格中的参数，逐条原文照录，编号规则见 output-format.md。这张表是数值出处和追溯的基础，一条也不能漏。
3. **划分配置项**，写入分析记录第 3 章：判断软件应划分为几个配置项并写出理由（引导程序和应用程序分开、不同处理器上的软件分开、在轨可上注部分是否单列）。FPGA 逻辑不属于本软件配置项，但要写清软硬件分工边界。一个配置项写一份规格说明。
4. **按检查表逐项分析。**按 [references/analysis-checklist.md](references/analysis-checklist.md) 逐项检查，结论写入分析记录第 7 章。每一项必须是三种结论之一：形成需求；写明“不适用”及理由；列为待确认问题。航天嵌入式软件常见的隐含需求尤其不能漏：上电初始化、看门狗、EDAC 与单粒子防护、关键数据冗余、指令合法性检查、通信超时恢复、资源余量。
5. **写规格说明。**按 srs-structure.md 从第 1 章写到附录 D，章节号、章节名、表名、表头照抄，不适用的章节保留标题写理由。重点：
   - **第 4 章运行环境**：硬件参数、中断、看门狗、存储器、定时器、编程编译要求、软硬件接口，全部取自输入材料；接口按 4.4.2 逐个写说明，涉及 1553B 时先读 [references/mil-std-1553b.md](references/mil-std-1553b.md)，按其中第 7 节逐项核对。
   - **第 5 章需求**：先画数据流图（5.1），再按第 1 层加工逐节写功能需求（5.2，IPO 格式 a～f），然后性能（5.3）、故障处理（5.4）、可靠性和安全性（5.5）、复用（5.6）、可维护性（5.7）。每条需求一个标识，一条只规定一件事，写外部可观察的行为，不写函数、变量等设计内容。安全关键功能加 `-K`，新状态功能加 `-N`。
   - **派生需求只写“需要规定什么”，不替上级做决定。**任务书没有规定的处理方式、阈值、默认值、保持哪些数据、恢复措施，一律写“【待确认】（见 Q-xxx）”；建议做法只能写在分析记录待确认问题清单的“建议”列。对照示例见下方“自行裁决的常见形式”。
   - **逐条找“没写的行为”。**写每条功能和性能需求时问一遍下面五件事，任务书、协议、基线规格说明都没写的，写【待确认】并列问题，不按“常见做法”补上：时间指标从什么时刻算到什么时刻（只给上限、没给起止点的指标不可测）；范围的端点算不算有效、超出范围怎么处理；掉电或复位后保持还是清零；同时发生、连续发生（如连续 N 次）时怎么计、何时清零。
   - **部门约定：计数满了回绕。**帧计数、指令计数、错误计数、事件计数等计到字段最大值后回绕（1 字节模 256，2 字节模 65536），任务书和协议没写时按此写，需求中写明“模 256”，分析记录派生理由写“计数满后回绕：部门约定”，不列待确认问题。任务书、协议或总体答复写了别的处理（如保持最大值）时照写并注明出处；没有出处不写“饱和”“保持 255”。
   - **第 6 章专项分析**：时序（接口时序、中断/任务、中断对时间性能的最坏情况影响）、数据访问冲突（识别原子属性的共享数据并提出使用要求）、时间系统、数据有效性（硬件层/协议层/应用层）。算不出的写“待实测”或【待确认】，不能不分析就写“满足要求”。
   - **第 7、8 章**：测试环境差异性、健壮性测试项目、不可测试项、测试要点（落实到需求标识）；安全关键功能对设计和测试的要求。
   - **附录**：数据字典（数据流图中的全部输入输出数据）、B.1 逆向跟踪矩阵（每条需求 → 任务书条款，含属性 R/M/N/K）、B.2 正向跟踪矩阵（每条任务书条款 → 需求）、C 更动记录、D 确认检查表（“对应章节”按本文档实际情况填，产保工程师一列留空）。
6. **建立追溯**，写入分析记录第 4、5 章：每条上级条款由哪些需求覆盖，覆盖情况；每条派生需求的理由。上级条款的要求在现有材料下无法完全实现（如要求下传的数据在帧格式中没有字段），或对应需求中还有【待确认】时，覆盖情况填“部分覆盖”，不填“已覆盖”。规格说明附录 B.1、B.2 与分析记录必须一致。
7. **质量自查。**按 [references/quality-rules.md](references/quality-rules.md) 逐条检查完整、无歧义、可验证、一致、可追踪、可行。能直接改写的就改写；需要用户提供信息才能改的，列入待确认问题。然后做三项核对，发现问题当场改正：
   - **问题与需求一致**：逐条看引用了问题编号（Q-xxx）的需求，描述中不能已经给出该问题的答案。例如 Q-018 写“恢复措施未规定”，对应需求就不能写“重新初始化串口并重同步”。
   - **数值有出处**：规格说明中的每个数值，都要能在分析记录第 2 章上级条款中找到，或者能由上级条款直接算出（如“2 字节、LSB 0.01 A”算出“最大 655.35 A”）。找不到出处的改为【待确认】。计数满了以后的回绕按上面的部门约定写，不算无出处。
   - **依据真实**：凡写“按……规定”“按……要求”的地方，依据必须出现在输入材料或本 Skill 的参考文件中。

   两份文件写完后**必须运行检查脚本**：

   ```
   node <本 Skill 所在目录>/scripts/check-report.mjs <软件需求规格说明.md> --record <需求分析记录.md>
   ```

   脚本核对规格说明的章节结构是否与部门模板一致、需求标识格式、IPO 是否完整、跟踪矩阵与正文和分析记录是否一致，以及疑似自行裁决、依据可疑、数值无出处、计数溢出处理无出处（R12）、计时起止点无出处（R13）、覆盖状态偏乐观、照抄模板示例、统计不一致。“必须处理”项逐条改正；“复核”项逐条判断，确实有依据的可以保留，但要在给用户的回复中逐条说明保留理由。改完再运行一次，直到没有“必须处理”项。最后把脚本的统计行（必须处理、复核各几项）告诉用户。
8. **统计**，写入分析记录第 8 章（项目名按 output-format.md，脚本按名字核对）。
9. **生成 Word 和 Excel（用户要求时）。**Markdown 是唯一的源文件，修改都在 Markdown 上做，再重新生成：
   - 调用 `mcp__docgen__render_docx`，`template` 用 `部门-软件需求规格说明`（`mcp__docgen__list_templates` 可查看它的字段），生成 `.docx`。`fields` 只填输入材料或用户给出的值：`文档名称`（规格说明没有一级标题时填“<软件名称>软件需求规格说明”）、`型号代号`、`内容提要`、`主题词`（如“XX 卫星 XX 分系统 XX 软件 需求规格说明”）；编号、密级、编写、审核等不填，留给用户在 Word 中补。
   - 待确认问题清单、需求条目（附录 B.1）、覆盖分析用 `mcp__docgen__export_xlsx` 导出，评审列见 output-format.md。
   - 把工具返回的“注意”如实告诉用户，尤其是缺少的模板字段和【待确认】标记的数量。

## 约束

- **结构照抄部门模板。**章节号、章节名、表名、表头与 srs-structure.md 一致，不增不减不改名；规格说明中不加模板没有的章节（待确认问题、上级条款摘录写在分析记录里）。
- **模板示例不是内容。**模板中“例如”后面的处理器、地址、时间、标准号、示例标识都不能抄进文档。
- **不编造。**波特率、周期、地址、子地址、指令码、阈值、精度、存储器容量、中断号等数值只能来自输入材料。没有就标“【待确认】”或“【待补充】”，不填“典型值”。可以在问题清单中给出建议值，但必须注明“建议值，需上级确认”。
- **不裁决矛盾。**输入材料之间不一致（包括任务书与 ICD 之间）时，引用两处原文，列为待确认问题，不自行选择其中之一。需求写成“不大于【待确认】ms（任务书 4.3 节为 10 ms，第 5 章为 20 ms，见 Q-003）”，不写“取较严值”。矛盾列为问题后，凡是受它影响的地方（检查条件、数据域长度、换算、测试要点）都写【待确认】，不在别处直接用其中一方的值。
- **标准条文以参考资料为准。**引用 MIL-STD-1553B 等标准的规定时，只能引用本 Skill 参考文件或输入材料中的内容；参考文件里没有的，写“需核对标准原文”，不凭记忆写数值。指出输入材料“违反标准”之前，先在参考文件中找到对应条文，找不到就写成待确认问题，不下结论。
- **不编造依据。**不写输入材料中没有的规定，如“按部门文档规范”“按 GJB xxx 要求”。GJB 5000B 是软件过程能力成熟度模型，不能作为某条产品需求的来源。
- **写“做什么”，不写“怎么做”。**任务书明确规定的实现方式写在 3.3 设计约束；除此之外，需求中不规定数据结构、函数划分和算法实现。
- **只读输入。**不修改用户提供的任务书和 ICD。
- **修订已有文档也要完整自查。**在已有规格说明上修改（任务书更新、补充材料、用户要求重做）时，第 7 步的核对和检查脚本同样要对全文执行；修订还要在附录 C 写本版本的更动记录、在修改历史加一行。用户要求“重新分析”时，从输入材料重新做，不要在旧文档上修补。
- **保存位置。**写到工作区的 `req/` 目录，文件名包含日期：`req/软件需求规格说明-20261103.md`、`req/需求分析记录-20261103.md`。生成的 Word 和 Excel 与 Markdown 同名，只换扩展名。
- **部门规定优先。**部门对标识规则、模板有新的规定时，以部门规定为准。

## 自行裁决的常见形式

以下写法都是在替上级做决定，自查时逐条排查（例子来自示例任务书的实际分析结果）：

| 不应这样写 | 问题 | 应这样写 |
|---|---|---|
| 软件应在收到请求后 10 ms 内发出遥测帧（取较严值） | 两处指标矛盾时自行选了一个 | 软件应在收到请求后【待确认】ms 内发出遥测帧（4.3 节 10 ms，第 5 章 20 ms，见 Q-003） |
| 检测到通信中断后应重新初始化串口并按同步字重新同步 | 任务书只写“自主恢复”，恢复措施是自己定的 | 检测到通信中断后应按【待确认】的措施恢复通信（见 Q-018） |
| 自检失败时应置失败标志并继续运行 | 失败后的处理方式是自己定的 | 自检失败时应按【待确认】的方式处理并下传自检结果（见 Q-021） |
| 应在复位后保持指令计数、错误计数和时间码 | 保持哪些数据是自己定的 | 复位后应保持【待确认】的运行数据（见 Q-031） |
| 应对 SRAM 全部 2 MB 空间执行读写校验 | 自检范围和方法是自己定的 | 初始化阶段应完成 RAM 自检，自检范围和方法【待确认】（见 Q-xxx） |
| 对非法指令应丢弃，错误计数加 1，指令计数不增加 | 处理方式是自己定的 | 判据和处理方式写【待确认】；可在 Q 的“建议”列写“建议：丢弃、错误计数加 1” |
| 空间余量应不小于 20%（照抄模板“一般情况下要求空间余量为 20%”） | 模板的一般要求不是本软件任务书的规定 | 任务书有规定按任务书写；没有就写【待确认】，在 Q 的“建议”列写“建议 20%（部门模板一般要求）” |
| 断电计数加 1，计满 255 后保持 255 | 部门约定是回绕，保持最大值没有出处 | 断电计数加 1（模 256）；总体要求保持最大值时，按答复写并注明“见 Q-xxx 答复” |
| 过流断电响应时间：自电流超过阈值起，至开关断开止，不大于 200 ms | 任务书只给了 200 ms，计时起止点是自己定的 | 过流断电响应时间不大于 200 ms，计时起点和终点【待确认】（见 Q-xxx） |
| 0x35 矛盾已列 Q-001，处理步骤里却写“检查数据域长度为 2” | 矛盾的一方（协议 V1.0 的 1 字节阈值）被直接用在别处 | 检查数据域长度为【待确认】（见 Q-001），阈值的字节数和 LSB 同样写【待确认】 |

派生需求本身可以写，例如“软件应处理 EDAC 双错”。但凡是“怎么处理”“处理成什么样”的内容，任务书没有规定的都写【待确认】。
