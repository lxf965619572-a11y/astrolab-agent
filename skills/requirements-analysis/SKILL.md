# 航天嵌入式软件需求分析

## 适用范围

- **输入**：软件研制任务书（或技术要求、任务分解）、接口控制文件（ICD）、单机或硬件说明、上级系统需求等。
- **输出**：需求分析报告，包括配置项、功能模块、外部接口、需求条目、追溯矩阵和待确认问题。用户要求时，再输出软件需求规格说明（SRS）初稿。
- **不做**：概要设计和详细设计。模块内部结构、函数划分、数据结构留到设计阶段。

产出可作为 GJB 5000B 体系中需求开发与需求管理活动的工作产品初稿，但必须由责任人确认，并按部门过程评审。

## 步骤

1. **确认输入和范围。**列出所有输入文件（名称、编号、版本、日期）。确认以下事项，不明确时先问用户，不要猜：
   - 单机名称、软件名称和简称（用于需求标识）
   - 目标平台：SPARC（BM3803/3823/3883）或 D2000
   - 软件安全关键等级
   - 本次输出：只出分析报告，还是同时出 SRS 初稿

   任务书引用了但没有提供的文件（如 ICD、指令码表、遥测参数表），记为待确认问题并告诉用户，不要凭经验补全。

   **读取输入文件**：`.docx`、`.xlsx`、`.pdf` 用 `mcp__docreader__read_document` 读取，不要用命令行解析二进制文件。长文档先用 `mode: "outline"` 看章节结构，再按 `nextOffset` 分段读完，不能只读开头。返回结果中的“注意”事项要在分析中考虑：图片里的框图、时序图没有被读出，相关内容列为待确认问题，请用户补充；合并单元格已经展开，核对表格时注意。旧版 `.doc`、`.wps` 读不了，请用户另存为 `.docx`。
2. **逐条摘录上级条款。**通读每份输入，把含“应、须、要求、不得、不大于、不小于”的语句，以及表格中的参数，逐条摘录为上级条款，原文照录，编号规则见 [references/output-format.md](references/output-format.md)。这张表是追溯的基础，一条也不能漏。
3. **划分配置项和功能模块。**判断软件应划分为几个配置项，并写出理由。常见的划分依据有：引导程序和应用程序分开，不同处理器上的软件分开，在轨可上注部分是否单列。FPGA 逻辑不属于本软件配置项，但要写清软硬件分工边界。在每个配置项内按能力划分功能模块，如初始化与自检、数据采集、遥测、遥控、时间管理、故障处理。这是需求分组，不是设计模块。
4. **梳理外部接口。**每个外部接口一行，写清接口标识、对端设备、物理类型（RS-422、1553B、CAN、LVDS、OC 指令、模拟量等）、方向、帧格式来源、速率或周期、字节序、校验方式、超时和差错处理。没有规定的格不填猜测值，填“【待确认】”，并写入待确认问题清单。
   涉及 1553B 总线时，先读 [references/mil-std-1553b.md](references/mil-std-1553b.md)，按其中第 7 节逐项核对任务书和 ICD。
5. **按检查表逐项分析。**按 [references/analysis-checklist.md](references/analysis-checklist.md) 逐项检查。每一项必须有三种结论之一：形成需求条目；写明“不适用”及理由；列为待确认问题。航天嵌入式软件常见的隐含需求尤其不能漏，包括上电初始化、看门狗、EDAC 与单粒子防护、关键数据冗余、指令合法性检查、通信超时恢复、资源余量。
6. **编写需求条目。**按 [references/output-format.md](references/output-format.md) 的标识规则和条目格式编写：
   - 每条需求只含一个“应”，写清触发条件、输入、处理、输出和量化指标。
   - 注明来源条款和合格性方法。
   - 任务书没有直接写、由分析得出的需求是派生需求，要标“派生”并写明理由。
   - **派生需求只写“需要规定什么”，不替上级做决定。**任务书没有规定的处理方式、阈值、默认值、保持哪些数据、恢复措施，在需求描述中一律写“【待确认】”，并关联问题编号；建议做法只能写在待确认问题清单的“建议”列。对照示例见下方“自行裁决的常见形式”。
7. **质量自查。**按 [references/quality-rules.md](references/quality-rules.md) 逐条检查完整、无歧义、可验证、一致、可追踪、可行。能直接改写的就改写；需要用户提供信息才能改的，列入待确认问题。
   然后做三项核对，发现问题当场改正：
   - **问题与需求一致**：逐条看引用了问题编号（Q-xxx）的需求，描述中不能已经给出该问题的答案。例如 Q-018 写“恢复措施未规定”，对应需求就不能写“重新初始化串口并重同步”。
   - **数值有出处**：需求描述中的每个数值，都要能在第 2 章上级条款中找到，或者能由上级条款直接算出（如“1 字节”算出“模 256”）。找不到出处的改为“【待确认】”。
   - **依据真实**：报告和 SRS 中凡写“按……规定”“按……要求”“按……执行”的地方，依据必须出现在输入材料或本 Skill 的参考文件中。

   报告写完后**必须运行检查脚本**（SRS 写完后也运行一次）：

   ```
   node <本 Skill 所在目录>/scripts/check-report.mjs <报告文件路径>
   ```

   脚本按固定规则列出疑似自行裁决、依据可疑、数值无出处、覆盖状态偏乐观、统计不一致的地方。“必须处理”项逐条改正；“复核”项逐条判断，确实有依据的可以保留，但要在给用户的回复中逐条说明保留理由。改完再运行一次，直到没有“必须处理”项。最后把脚本的统计行（必须处理、复核各几项）告诉用户。
8. **建立追溯。**正向追溯：每条上级条款由哪些软件需求覆盖。反向追溯：每条软件需求来自哪条上级条款，或者是派生需求。列出未覆盖的上级条款。上级条款的要求在现有材料下无法完全实现（如要求下传的数据在帧格式中没有字段），或对应需求中还有【待确认】时，覆盖情况填“部分覆盖”，不填“已覆盖”。
9. **输出。**按 output-format.md 写需求分析报告。用户要求时，再按 [references/srs-gjb438b.md](references/srs-gjb438b.md) 生成 SRS 初稿。报告最后给出统计：配置项数、功能模块数、外部接口数、需求条目数（按类别）、待确认问题数（按类型）、上级条款覆盖率。
10. **生成 Word 和 Excel（用户要求时）。**先把 Markdown 保存好，它是唯一的源文件，修改都在 Markdown 上做，再重新生成：
    - 调用 `mcp__docgen__list_templates`，选择对应文档类型的模板，查看模板需要哪些封面字段。
    - 调用 `mcp__docgen__render_docx` 生成 `.docx`。`fields` 只填输入材料或用户给出的值（软件名称、文件编号、版本等），没有依据的字段不填，让它显示为“【待补充】”。“文档名称”填文档类型本身，如“软件需求规格说明”，不要重复软件名称。
    - 需求条目表、追溯矩阵、待确认问题清单调用 `mcp__docgen__export_xlsx` 导出为 `.xlsx`，便于评审时逐条填写处理意见。用 `include` 分别导出这三类表；表头相同的表会合并为一个工作表。导出待确认问题清单时加 `reviewColumns: ["答复", "答复人", "状态"]`，导出需求条目表时加 `reviewColumns: ["评审意见", "处理结果"]`。
    - 把工具返回的“注意”如实告诉用户，尤其是缺少的模板字段和【待确认】标记的数量。

## 约束

- **不编造。**波特率、周期、地址、子地址、指令码、阈值、精度等数值只能来自输入材料。没有就标“【待确认】”，不填“典型值”。可以在问题清单中给出建议值，但必须注明“建议值，需上级确认”。
- **不裁决矛盾。**输入材料之间不一致（包括任务书与 ICD 之间）时，引用两处原文，列为待确认问题，不自行选择其中之一。需求描述写成“不大于【待确认】ms（任务书 4.3 节为 10 ms，第 5 章为 20 ms，见 Q-003）”，不写“取较严值”。
- **标准条文以参考资料为准。**引用 MIL-STD-1553B 等标准的规定（时间、位定义、方式码、上限值）时，只能引用本 Skill 参考文件或输入材料中的内容；参考文件里没有的，写“需核对标准原文”，不凭记忆写数值。指出输入材料“违反标准”之前，先在参考文件中找到对应条文，找不到就写成待确认问题，不下结论。
- **不编造依据。**不写输入材料中没有的规定，如“按部门文档规范”“按部门配置管理规定”“按 GJB xxx 要求”。GJB 5000B 是软件过程能力成熟度模型，规定的是研制过程，不能作为某条产品需求的来源。SRS 用的是演示模板或本 Skill 的章节结构时，不要写成“按部门正式模板”。
- **写“做什么”，不写“怎么做”。**任务书明确规定的实现方式写成设计约束；除此之外，需求中不规定数据结构、函数划分和算法实现。
- **只读输入。**不修改用户提供的任务书和 ICD。
- **修订已有报告也要完整自查。**在已有报告基础上修改（任务书更新、补充材料、用户要求重做）时，第 7 步的三项核对和检查脚本同样要对全文执行，不能只检查改动的部分，旧版中的问题要一并改正。用户要求“重新分析”时，从输入材料重新做，不要在旧报告上修补。
- **保存位置。**用户要求保存时，写到工作区的 `req/` 目录，文件名包含日期，如 `req/需求分析报告-20261024.md`、`req/软件需求规格说明-初稿-20261024.md`。生成的 Word 和 Excel 与 Markdown 同名，只换扩展名。
- **部门规定优先。**部门有正式 SRS 模板或需求标识规则时，以部门规定为准，本 Skill 的参考文件只作补充。

## 自行裁决的常见形式

以下写法都是在替上级做决定，自查时逐条排查（例子来自示例任务书的实际分析结果）：

| 不应这样写 | 问题 | 应这样写 |
|---|---|---|
| 软件应在收到请求后 10 ms 内发出遥测帧（取较严值） | 两处指标矛盾时自行选了一个 | 软件应在收到请求后【待确认】ms 内发出遥测帧（4.3 节 10 ms，第 5 章 20 ms，见 Q-003） |
| 检测到通信中断后应重新初始化串口并按同步字重新同步 | 任务书只写“自主恢复”，恢复措施是自己定的 | 检测到通信中断后应按【待确认】的措施恢复通信（见 Q-018） |
| 自检失败时应置失败标志并继续运行 | 失败后的处理方式是自己定的 | 自检失败时应按【待确认】的方式处理并下传自检结果（见 Q-021） |
| 应在复位后保持指令计数、错误计数和时间码 | 保持哪些数据是自己定的 | 复位后应保持【待确认】的运行数据（见 Q-031） |
| 应对 SRAM 全部 2 MB 空间执行读写校验 | 自检范围和方法是自己定的 | 初始化阶段应完成 RAM 自检，自检范围和方法【待确认】（见 Q-xxx） |
| 对非法指令应丢弃，错误计数加 1，指令计数不增加 | 处理方式是自己定的 | 判据和处理方式写【待确认】；可在 Q 的“建议”列写“建议：丢弃、错误计数加 1” |

派生需求本身可以写，例如“软件应处理 EDAC 双错”。但凡是“怎么处理”“处理成什么样”的内容，任务书没有规定的都写【待确认】。
