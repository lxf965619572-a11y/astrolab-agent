# 技能创作

技能是写给智能体的工作说明书：什么时候用、输入什么、一步一步怎么做、做完怎么自查、什么不能做。好技能让不同的人、不同的时间做同一件事，结果一样可靠。

## 适用范围

- **工作区**：“我的库”。新技能放在 `skills/<技能名>/`，技能名用小写英文和连字符（如 `spacewire-review`）。
- **输出**：`SKILL.md`；需要时 `references/`（规则表、模板、示例）、`scripts/`（自查脚本，只用 Node 内置模块）；`tests/` 下 1～3 个试用用例（输入材料 + 期望要点）。
- **不做**：不改内置技能和别人的技能（要改进时复制到我的库里改，名字不同）；不把真实型号的代码或数据写进技能（规则和方法可以，示例用脱敏或虚构的）。

## 步骤

1. **弄清要做成技能的工作。**用 `ask_user_question` 问清楚（一次问 2～4 个，不要一次问太多）：
   - 这项工作是什么、什么时候做，用户平时怎么说（决定 description 里的触发说法）。
   - 输入是什么（文件类型、必需和可选），输出是什么（文件、格式、放哪）。
   - 用户现在怎么做：步骤、看哪些规范或检查表、容易出错的地方、做得好的标准。
   - 有没有现成的规范、模板、好的样例可以参考（让用户给文件路径，读进来）。
   先用 `mcp__knowledge__search_knowledge` 查知识库里相关的经验，看看已有技能（内置的在工作台安装目录的 `skills/` 下）有没有能复用的写法。
2. **定结构，给用户看。**列出：技能名、description、步骤大纲、约束、要不要参考资料和检查脚本。用户同意后再写。
3. **写 SKILL.md。**格式照内置技能（例如 `unit-test-design`、`coding`）：
   - 头信息只有 `name` 和 `description`。description 一段话：做什么 + 什么时候用（列出用户会说的几种说法）。智能体靠它决定用不用这个技能，写具体。
   - 正文：适用范围（输入、输出、不做）→ 步骤（编号，每步一个动作，写清用什么工具、遇到不明确时先问）→ 约束（不能做的事，写原因）→ 常见错误做法（表格：不应这样做 / 问题 / 应这样做）。
   - 规则多、模板长的放 `references/`，在步骤里用相对链接引用，说明什么时候读。
   - 写给智能体看：说“做什么、为什么”，不写空话（如“认真仔细”）。部门规定优先。
4. **写检查脚本（输出是文档或代码时建议写）。**`scripts/check-*.mjs`，只用 Node 内置模块，只读不改文件；按固定规则列“必须处理”和“复核”，最后一行统计；退出码 0/1/2。照内置技能的 check 脚本写。
5. **写试用用例。**`tests/<用例名>/`：输入材料（虚构或脱敏）+ `expected.md`（做对了应该有的要点、不应出现的错误）。
6. **自查并试用。**按下面的检查表逐项过一遍；用 `node scripts/...` 跑脚本的自测。告诉用户：在工作台“技能与插件 → 我做的”里点“试用”安装这个技能，再用试用用例发起一个任务看效果；根据效果改。
7. **收尾。**回复里列出写了哪些文件、怎么试用、还有哪些待用户确认的地方。提交到共享库由用户在工作台操作（要审核），不要自己提交 Git。

## 自查检查表

| 项 | 要求 |
|---|---|
| name | 小写英文、数字、连字符，和目录名一致，不和内置技能重名 |
| description | 说清做什么和什么时候用，包含用户的常见说法；一段话，不超过 300 字 |
| 输入 | 必需输入缺了怎么办写清楚（先问，不猜） |
| 步骤 | 编号；每步能执行、能检查；用到的工具写全名（如 `mcp__utest__run_unit_tests`） |
| 约束 | 写明不能做的事和原因；涉及改代码、改设计、提交 Git 的要明确 |
| 结果真实 | 要求数字来自工具结果，不估计；没运行写“未运行” |
| 安全 | 不在外网处理真实型号内容；脚本不联网、不删文件、只读 |
| 篇幅 | SKILL.md 正文尽量在 150 行以内，细节放 references |
