# 航天嵌入式软件概要设计

## 适用范围

- **输入**：软件需求规格说明（SRS）、硬件接口文件（存储器映射、中断分配、寄存器、时序）、通信协议或 ICD；可能还有研制任务书。
- **输出**（两份，同时写，结构见 [references/hld-doc-structure.md](references/hld-doc-structure.md)）：
  - 《软件概要设计说明》：正式文档，**严格按部门模板 02-1**（含模板批注提出的写法要求），每个配置项一份。
  - 《概要设计记录》：工作底稿，记录设计依据原文、设计决策理由、时序分析计算、资源估算、待确认问题。
- 设计说明是详细设计的输入：每个模块的功能、对外接口（函数原型、调用者、执行环境）、对应需求、所在任务和中断、共享数据保护、可靠性措施，要写到详细设计可以直接据此展开的程度。
- **不做**：不写函数内部的处理步骤，不定义数据类型、宏、常量和结构体（部门模板已从概要设计中删除，留给详细设计）；不写需求（SRS 有缺漏时列为待确认问题）；不修改上级文件。
- **只做正向设计。**工作区中已有代码时，先问用户：是按上级文件重新设计，还是为已有代码补写概要设计。补写时，代码只用来确定模块划分和接口；代码与上级文件不一致的地方列为待确认问题，写明“现有代码的做法”，设计正文仍按上级文件写。

## 步骤

1. **确认输入和范围。**列出输入文件（名称、编号、版本）、配置项名称、目标平台（SPARC BM3803/3823/3883 或 D2000）、有无操作系统、软件研制类型和安全关键等级（决定第 4 章是否要写）。不明确时先问用户。读取文件：`.docx`、`.xlsx`、`.pdf` 用 `mcp__docreader__read_document`，长文档先看 outline 再分段读完。**SRS 的每一条需求都要读到**，不能只读目录或摘要。
2. **摘录设计依据**，写入记录第 2 章，原文照录：
   - 2.1：SRS 的**全部**需求（需求标识 + 原文），包括性能、可靠性、安全性、接口、约束类需求；
   - 2.2：硬件接口文件和协议中与软件设计有关的条款：存储器映射、中断分配、外设的缓冲深度和时序要求、复位状态、看门狗、非易失存储器的写入特性、通信速率和帧格式。

   这一章是数值出处和需求追溯的基础，检查脚本据此核对。
3. **核对上级文件之间的一致性。**逐项比较 SRS 与每份接口文件：速率、帧长和字段（把字段长度加起来核对总长）、编号方式、数值的单位和含义、时间要求；SRS 中只写“应进行故障处理”这类没有具体内容的要求。不一致或没有规定的列为待确认问题（Q-xxx），引用两处原文。**不替上级选择**；为使设计能够继续，可以写“暂按 SRS 设计（Q-xxx 确认前）”，同时写出另一种规定对设计的影响。
4. **定设计决策**，写入记录第 3 章（D-xxx，每条写理由）：执行模型（前后台、时间片、操作系统任务）、时基、哪些外设用中断、是否允许中断嵌套、共享数据保护的统一方法、故障处理的统一方法。决策的结果写进设计说明对应章节（5.1.1、5.1.2.1、5.2.2、5.6.2）。新研且 A、B 级的软件，把关键问题和至少两个备选方案写进设计说明第 4 章。
5. **划分模块并分配需求。**按 [references/architecture-checklist.md](references/architecture-checklist.md) 第 1 节划分：驱动与业务逻辑分开；每个硬件输出只有一个模块写它；安全约束（互锁、数量限制、模式限制）放在所有路径都必须经过的那个模块中。写设计说明 5.1.2：顶层任务调度、顶层调用结构图、每个任务的层次结构图和模块表（模块名称、功能、对外接口原型、调用者、执行环境、对应需求），5.1.2.3 源文件构成，附录 B 模块汇总表。**SRS 的每一条需求都要按标识分配到模块**（附录 A.2），每个模块都要有需求依据（附录 A.1）；不能追到章节号。
6. **设计接口**，写设计说明 5.2：外部硬件接口（CPU 以外的存储芯片、总线、IO、FPGA 寄存器都算）及各类接口的处理方式；外部软件接口（与其他配置项、库之间的函数、共用数据结构、缓冲区地址；与 FPGA 的不算）；**数据有效性判断表逐项回答模板表头下的每一个提问**。
7. **设计中断、任务和共享资源**，写设计说明 5.2.2：中断列表、任务列表、临界资源矩阵、访问冲突分析（列出变量和保护措施）。
8. **设计时间系统**（5.3）。不使用星时这类时间的写“无时间系统”。
9. **设计运行方案**，写设计说明 5.4：顶层运行流程图（必须）、每个任务和中断的运行设计、运行模块组合、内存空间分配（程序区、数据区、三取二区，地址来自接口文件）、堆栈预算和分配、运行时间预算和分配。**从最严的响应时间要求倒推每一步允许的最长执行时间**：主循环中任何一步（包括外设等待）都不能超过它，超过的改为分步执行（状态机），不能忙等。预算必须小于分配。
10. **做时序分析和资源估算**，写入记录第 4、5 章。按 [references/timing-analysis.md](references/timing-analysis.md)，对 SRS 中每一条有时间要求的需求、接口文件中每一条时间约束给出最坏情况路径、计算过程和结论；估计值写明估计方法，结论写“满足（估计，待实测）”；算不出的写“待实测”并说明在哪项测试中测量，**不能不分析就写“满足”**。资源逐项估算 CPU 负荷、程序存储器、数据存储器（含栈）、非易失存储器，与 SRS 5.3.2 的余量要求比较。设计说明 5.4.4 的预算取自这里。
11. **数据构成和可靠性安全性设计**：5.5 只写对外部输入输出数据的构成表。5.6.1 先逐条罗列 SRS 的故障处理、可靠性、安全性需求（带标识），再补充设计中新识别的；5.6.2 **写具体措施**（哪些变量三取二、存在哪里、三区不一致怎么处理；标志用 0x55/0xAA 不用全 0 全 1；在哪里喂狗；指令判哪些字段），并按检查表第 9～11 节检查看门狗、EDAC 和存储器刷新、关键数据冗余、指令防护、上电和复位状态、故障检测和处理。上级文件没有规定处理方式的，列为待确认问题，可以在“建议”中给方案。5.7 可复用设计写出实际的库及版本。
12. **跟踪矩阵和附录**：附录 A.1（模块 → 需求）、A.2（每条需求 → 模块，属性列 R/N/M/K）、B 模块汇总表、C 更改记录、D 确认检查表（“对应章节”按本文档实际情况填，产保工程师一列留空）。
13. **自查（必须）。**按 [references/quality-rules.md](references/quality-rules.md) 检查，然后运行：

    ```
    node <本 Skill 所在目录>/scripts/check-hld.mjs <概要设计说明> --record <概要设计记录> --srs <SRS 文件>
    ```

    `--srs` 用输入的 SRS 原文件（.docx 或 .md），脚本据此核对记录 2.1 节是否漏摘需求。直接运行脚本，不需要读它的源码；不要为了让脚本不报而改写法（如给数值加“约”字），而要按提示核实内容。“必须处理”项逐条改正，“复核”项逐条判断，保留的在回复中说明理由。改完再运行一次，直到没有“必须处理”项，并把统计行告诉用户。
14. **输出。**Markdown 是唯一的源文件，保存为 `<配置项目录>/doc/软件概要设计说明-<软件简称>-<日期>.md` 和 `<配置项目录>/doc/概要设计记录-<软件简称>-<日期>.md`。用户要求时：`mcp__docgen__render_docx` 套 `部门-软件概要设计说明` 模板生成 Word（模板字段：`文档名称`（Markdown 文首有唯一的一级标题时自动填）、`内容提要`、`主题词`、`型号代号`，只填有依据的；编号、密级、编写、审核等不填，留给用户在 Word 中补）（流程图和结构图自动转换，转换失败的原因会在“注意”中列出，要改正后重新生成）；待确认问题用 `mcp__docgen__export_xlsx` 导出，加 `reviewColumns: ["答复", "答复人", "状态"]`。

流程图和结构图写法见 [references/flowchart-guide.md](references/flowchart-guide.md)。

## 约束

- **结构照抄部门模板。**章节号、章节名、表名、表头与 hld-doc-structure.md 一致；设计说明中不加模板没有的章节（设计依据、设计决策表、时序分析计算、待确认问题写在记录里）。模板“例如”后面的内容是写法示范，不能抄进文档。
- **不编造。**地址、中断级别、时序、容量、速率只能来自输入文件或记录中的设计决策；设计决策中的数值写理由。执行时间、堆栈等估计值写明估计方法，并注明“估计”。没有依据的写【待确认】并关联 Q-xxx。
- **不裁决矛盾。**上级文件之间不一致时列为待确认问题，引用两处原文，不写“以 SRS 为准”“取较严值”。
- **不放宽需求。**时序分析不满足时，改设计或列为待确认问题，不改用较宽的指标。
- **需求全部按标识追踪。**SRS 的每一条需求都在 A.2 中出现，包括性能、可靠性、安全性、接口、约束类需求；不追到章节号。
- **写到概要设计为止。**模块的对外接口写到函数原型；函数内部的处理步骤、数据类型和结构体留给详细设计。但影响时序和资源的实现方式（分步执行、中断驱动、双缓冲）要在概要设计中定下来。
- **只读输入。**不修改上级文件。
- **新写设计不沿用旧版本。**用户没有要求修订时，不读取、不沿用工作区中其他版本的概要设计（包括备份目录中的），从输入文件重新做。用户要求在已有设计上修订时，才以它为基础，并在附录 C 写本版本的更改说明。
- **只读输入和本 Skill 的参考文件。**不读取工作区以外的评测目录、参考设计作为样例；格式以本 Skill 的参考文件为准。
- **修订也要完整自查。**在已有设计上修改时，对全文重新执行第 13 步。
- **不在外网处理真实型号代码和文档。**使用云端模型时只处理样例或脱敏材料。
- **部门规定优先。**部门对模板、设计规范有新的规定时，以部门规定为准。

## 常见错误做法

| 不应这样写 | 问题 | 应这样写 |
|---|---|---|
| SRS 写“1553B 消息 2 ms 内准备好应答数据”，设计把消息处理放在 50 ms 周期任务中 | 运行设计不满足时间要求，且没有分析 | 记录中算出最坏情况时延；不满足时改为中断中准备数据或缩短处理间隔 |
| 时序分析写“处理时间很短，满足要求” | 没有路径、没有数值，无法核对 | 写出最坏情况路径和每段时间（估计值注明估计方法），结论“满足（估计，待实测）” |
| “陀螺数据采集：依次读 6 个通道，每个通道等待 2 ms 稳定” | 主循环中忙等 12 ms，其他时间要求无法满足 | 按 tick 分步：每次只切换或读取一个通道，等待由计时判断 |
| “在 10 ms 定时中断中喂狗” | 主循环死循环时中断仍在喂狗，看门狗失效 | 在主循环中喂狗，喂狗间隔小于看门狗最短超时并留余量 |
| 可靠性设计写“要求对重要参数采用多数表决” | 把要求抄了一遍，没有措施（批注） | “模式字 mode、工作标志 work_flag 三区保存（地址见表 5.4-2），每周期三取二，三区不一致时以表决值回写三区并计数下传” |
| 标志取值用 0 和 1 | 单粒子翻转后容易误判（批注） | 有效 0x55、无效 0xAA，其他值按无效处理 |
| A.2 跟踪矩阵写“3.2 节功能需求 → 遥测模块” | 追到大章节（批注） | 每条需求一行：XXYY-FREQ012 → tm_proc |
| 把软件与 FPGA 之间的寄存器接口写在外部软件接口 | 分类错误（批注） | 写在 5.2.1.1 外部硬件接口 |
| 内存分配表列出每个全局变量的地址 | 不是这张表的用途（批注） | 只写程序区、数据区、三取二区、隔离区等区段 |
| 堆栈预算 2048、分配 2048 | 预算应小于分配（批注） | 调整分配或改设计，使预算有余量 |
| 5.5 写基本数据类型、宏、结构体 | 部门模板已删除这些小节 | 5.5 只写对外输入输出数据的构成表；类型和结构体留给详细设计 |
