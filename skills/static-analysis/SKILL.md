# 嵌入式 C 软件静态分析

## 输入和输出

- **输入**：被分析的源代码；目标平台；软件名称、版本、安全关键等级；部门工具的度量结果（有就用，见下）；详细设计说明（判断特殊设计、代码审查时用）。
- **输出**：
  - 静态分析记录（工作底稿）`review/静态分析记录-<配置项简称>-<日期>.md`。
  - 静态分析报告（部门模板 02-3）`review/<软件名称>（<版本>）静态分析报告.md`：由脚本从记录和度量数据生成。
- 格式见 [references/sa-format.md](references/sa-format.md)；编程规则用代码走查 Skill 的规则表 `code-walkthrough/references/gjb8114-c.md`。

下文 `<走查脚本目录>` 指 `code-walkthrough/scripts`（与本 Skill 同在 skills 目录下），`<脚本目录>` 指本 Skill 的 `scripts`。

## 步骤

1. **确认范围和数据来源。**被分析的目录、目标平台、软件名称和版本、测试版本（首次或第几次回归）。问用户有没有 TESTBED、SpecChecker 等部门工具的结果：
   - 有：请用户提供导出文件，按 sa-format.md 整理成度量 CSV，逐行核对，不估计、不补数；违反规则的结果按告警逐条写进记录第 4 节（编号 TB-nnn、SC-nnn）。
   - 没有：用本 Skill 自带的脚本统计，报告会注明口径；基本复杂度没有数据，报告中为【待补充】，要告诉用户。
2. **运行工具。**
   - `node <走查脚本目录>/metrics.mjs <源码目录> --json review/metrics.json --md review/metrics.md`（有部门工具 CSV 时也运行，用于核对函数清单）。
   - `node <走查脚本目录>/gjb-scan.mjs <源码目录> --json review/gjb-scan.json --md review/gjb-scan.md`。
   - `mcp__cppcheck__run_cppcheck`（`target` 填目标平台），结果在 `.cppcheck/last-run.json`。
   - `mcp__utest__compile_check`（可用时），严格告警中与编程规则有关的写进第 4 节（编号 CC-nnn）。
3. **分析超标模块。**度量数据中每个超过门限的模块（行数 > 200、圈复杂度 > 10 且基本复杂度 > 4、扇出 > 5、注释率 < 30%）打开源码看，写进记录第 3 节：超标原因、对功能和可维护性的影响、是否修改。
4. **甄别规则违反和告警。**gjb-scan 的每一处、Cppcheck 的每一条、部门工具报的每一条，打开源码判定为违反、特殊设计、误报或问题，写进记录第 4 节。特殊设计要写设计依据（详细设计条目号），并说明对软件功能、性能没有影响；拿不准是不是特殊设计的，写【待确认】并列入第 6 节。
5. **代码审查。**对照详细设计检查代码的一致性和逻辑正确性（重点是 Cppcheck 判定为“问题”的、超标模块），发现的问题写进第 5 节。全面的人工走查是代码走查 Skill 的工作，这里不重复。
6. **填统计，运行检查脚本（必须）。**

   ```
   node <脚本目录>/check-sa.mjs review/静态分析记录-<简称>-<日期>.md
   ```

   核对：每个超标模块都有分析，每条告警都已甄别，统计数字一致。“必须处理”全部改完。
7. **生成报告。**

   ```
   node <脚本目录>/gen-sa-report.mjs review/静态分析记录-<简称>-<日期>.md --out "review/<软件名称>（<版本>）静态分析报告.md"
   ```

   第 3 章统计和第 4 章表格**不手改**，记录或度量数据变了就重新生成（加 `--force`）。然后填写【待补充】（1.2 系统概述、3.1 被测软件说明从需求规格说明取；开发环境、软件规模等问用户），按统计改写 3.4 测试结论、3.5 评价和建议、第 5 章总结：仍有未修改的违反强制类规则（特殊设计除外）或代码审查问题时，结论不能写“通过，无遗留问题”。再运行一次检查脚本并加 `--report <报告路径>`。
8. **导出（用户要求时）。**`mcp__docgen__render_docx` 套 `部门-静态分析报告` 模板生成 Word，`fields` 用报告文首注释中给出的内容提要、主题词（编号、密级、编写、审核等不填）；第 4 章的表格可用 `mcp__docgen__export_xlsx` 导出。

## 约束

- **数字有出处。**度量数字只来自部门工具的导出文件或 metrics.mjs，不估计、不心算；口径不同的数据不混用。
- **只读。**不修改被分析的源文件。
- **特殊设计要有依据。**“main 函数本来就是无限循环”这类理由必须对应到设计条目，并说明不影响功能、性能。
- **不夸大工具能力。**静态分析的规则检查以工具扫描加人工确认为主，规则表中只能人工检查的规则由代码走查覆盖；报告 3.2 已写明这一点，改写结论时不要扩大为“全部规则均已检查”。
