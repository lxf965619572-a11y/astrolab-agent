# 航天嵌入式软件研制总结

研制总结汇总整个研制过程，内容几乎全是事实：版本、日期、单号、问题数、测试结论。报告写错一个日期或数字，评审时就要逐项核对，所以**每个事实都要有出处，找不到的写【待补充】问用户，不编、不估、不照抄模板示例**。

## 输入和输出

- **输入**：
  - 研制类型（Ⅰ类完全沿用、Ⅲ类在基线软件上更改、Ⅳ类全新研制；只做这三类）。
  - 工作区中本工具产出的文档：需求规格说明，走查、静态分析、单元测试、确认测试的记录和报告，metrics.json。
  - 数据包中的文件（用户提供目录）：任务书、评审记录、出入库单、单机/分系统/系统测试报告、第三方评测报告和问题单、归零报告、产保要素确认表、研制过程确认表、装机质量跟踪卡等。Word、PDF 用 `mcp__docreader__read_document` 读。
- **输出**：
  - 研制信息表（工作底稿）`doc/研制信息表-<简称>.md`，可导出 Excel 给用户填写。
  - 研制总结报告 `doc/<软件名称>（<版本>）研制总结报告.md`，由脚本从信息表生成；导出 Word 套部门模板。
- 信息表各节与报告章节的对应、两类报告的结构、评审要点见 [references/summary-format.md](references/summary-format.md)。

下文 `<脚本目录>` 指本 Skill 的 `scripts`。

## 步骤

1. **确认研制类型和范围。**问清研制类型、验收版本、全部版本，以及数据包文件在哪里。研制类型拿不准的（比如“改了一点”）不要替用户判断：Ⅰ类是完全沿用不改代码，改了代码的是Ⅲ类。用户说的是Ⅱ类或Ⅴ类时，说明本 Skill 只支持Ⅰ、Ⅲ、Ⅳ类。
2. **生成研制信息表。**

   ```
   node <脚本目录>/info-sheet.mjs --class <I|III|IV> --ws <工作区> --out doc/研制信息表-<简称>.md [--srs <需求规格说明.md>]
   ```

   脚本从工作区文档预填能找到的内容，标“〔自动：文件〕”；其余为【待补充】。已有信息表时不要加 `--force` 覆盖，除非用户确认表中没有已填的内容。
3. **补全信息表。**逐个读数据包中的文件，按信息表各节摘录：
   - 摘录的内容后标“〔来源：文件名 章节或页码〕”；用户口头给出的标“〔用户提供〕”。
   - 模板的示例（《XX》、“XX软件”）换成实际名称；实际没有发生的写“无”或“未参加”（问过用户再写）；没有的文档从数据包清单中删去该行并在备注说明。
   - 产保要素确认、研制过程确认的数字照确认表抄，不自己数。
   - 找不到出处的保留【待补充】。全部读完后，把【待补充】按节列成清单一次问用户（用户也可以导出 Excel 填写：`mcp__docgen__export_xlsx`，`merge: false`；填好后用 `mcp__docreader__read_document` 读回）。
   - 问事实时**不给具体答案当推荐项**：数据包里没有的事实（是否参加系统测试、合计对不上时该改成几、某个日期），选项里的推荐项只能是“我来提供”或“先写【待补充】”；“未参加”“改为 6”这类具体答案可以列为选项，但不标推荐。用户点了推荐项，事实就成了猜的。数据包里互相矛盾的（合计对不上、评审早于被评审文档），列出两处原文问用户，不替用户选。
4. **检查信息表（必须）。**

   ```
   node <脚本目录>/check-summary.mjs doc/研制信息表-<简称>.md
   ```

   “必须处理”项改完；“复核”项逐条判断，需要用户确认的告诉用户。
5. **生成报告。**

   ```
   node <脚本目录>/gen-summary.mjs doc/研制信息表-<简称>.md --out "doc/<软件名称>（<版本>）研制总结报告.md"
   ```

   报告中的表格和数字**不手改**：信息表改了就重新生成（加 `--force`）。生成后只在报告里写信息表中没有的文字：缩略语、各测试结论（单元测试写明三覆盖情况和结论；确认测试引用确认测试报告的结论）、系统测试结论、结论中“是否具备验收条件”。这些文字要以信息表和已有报告为依据；Ⅰ类结论中“完全沿用”的说法要与信息表一致。
6. **检查报告（必须）。**

   ```
   node <脚本目录>/check-summary.mjs doc/研制信息表-<简称>.md --report "doc/<软件名称>（<版本>）研制总结报告.md"
   ```

   重点：结论中只写实际通过的测试（没有参加系统测试、第三方评测的不能写）；未固化的固化一章用“应……”，不能出现“了”；结论中软件名称后带代号和版本。
7. **导出（用户要求时）。**`mcp__docgen__render_docx`：Ⅰ类用模板 `部门-研制总结报告-I类`，Ⅲ、Ⅳ类用 `部门-研制总结报告-III-IV类`；fields 用报告开头注释中的值。研制流程图、装机质量跟踪卡、第三方问题单和评测结论原件、研制过程确认表在 Word 中插入或附上。

## 约束

- **不编事实。**日期、单号、问题数、覆盖率、检查项数量只来自文件或用户；性能符合情况要写实测值，不照抄要求的范围。
- **出处标记只在信息表中。**报告由脚本生成，标记不会进入报告；不要把信息表的内容手抄进报告。
- **不替用户下结论。**是否具备验收条件、“不符合”项如何处理，由用户确认后再写。
- **只读数据包。**不修改数据包中的文件。
