# 信息流图服务（infoflow，内置）

把需求文档梳理出的分组、节点和流向存成一份**信息流模型**，再从模型生成几种视图：全图、总图、分图、链路图和 N² 接口矩阵。每个视图输出一个 `.md`（图片 + Mermaid 源码 + 统计 + 待确认清单）和一个 `.svg`。智能体用工作台的文档读取服务读任务书/ICD，把整理好的模型交给本服务；本服务负责校验、布局、出图和可读性度量，不联网、不依赖 npm 包。配套技能是 `skills/info-flow`（信息流梳理）。

原是“我的库”里的插件 info-flow-diagram 1.2.0，2026-11-17 起改为内置：技能放在 `skills/info-flow`，服务放在这里，由 `config/cordis.patch.yml.template` 的 `mcp-infoflow` 注册，随安装包发布，不用再从库里安装。

## 为什么要分视图

一张图里，连线交叉的数量大致随连线数的平方增长；大型项目画成一张图，必然理不清。本服务的做法是：

- **模型写全，图取部分。** `<名称>.flow.json` 是唯一的权威来源；图都是生成物，改模型后重新出图。
- **每张图只回答一个问题。** 总图看分组之间，分图看一个分组和它的接口，链路图看一条指令/数据经过哪些环节，N² 矩阵核对接口是否齐全。
- **清不清楚有客观指标。** 每张图都量出连线交叉数、穿过节点的线、重叠的标签；超过阈值时提醒，并给出建议的拆法。

## 试用

3. 以前装过“我的库”里的 info-flow-diagram 插件的，在“技能与插件”里卸载它，免得同名技能和两套工具同时出现。

## 工具

引擎配置里注册的服务名是 `infoflow`，智能体看到的完整工具名是：

| 工具 | 作用 |
|---|---|
| `mcp__infoflow__validate_info_flow` | 校验模型，不写文件；模型太大时给出建议的视图 |
| `mcp__infoflow__render_info_flow` | 出图；第一次直接给规格时同时保存模型文件 |
| `mcp__infoflow__render_info_flow_matrix` | 出 N² 接口矩阵 |
| `mcp__infoflow__export_info_flow_html` | 出交互版（一个 HTML 文件，含全部视图）；`view: "suggested"` 时自动生成 |

### 共同参数：模型从哪来

二选一：

| 参数 | 说明 |
|---|---|
| `title`、`source`、`direction`、`order`、`groups`、`flows` | 直接给规格（见下面“模型”） |
| `specFile` | 工作区里的模型文件 `<名称>.flow.json`。改过模型、换视图出图都用它 |

### `render_info_flow`

| 参数 | 类型 | 说明 |
|---|---|---|
| `view` | `full` / `overview` / `group` / `chain` / `suggested` | 默认 `full`。`suggested` 按模型规模一次出齐建议的视图和 N² 矩阵 |
| `group` | string | `view=group`：分组 id 或名称 |
| `focus` | string[] | `view=chain`：起点节点 id 或名称 |
| `to` | string[] | `view=chain` 可选：终点；给了只画起点到终点的**最短路径** |
| `towards` | `down` / `up` / `both` | `view=chain` 且没给 `to`：下游（默认）、上游、两头 |
| `depth` | integer | `view=chain` 可选：最多走几步 |
| `minWeight` | integer | `view=overview` 可选：一对分组之间至少几条流向才画线；默认自动 |
| `order` | `auto` / `given` | 覆盖模型里的排列方式 |
| `outputDir` | string | 输出目录（工作区内），默认 `diagrams`；用 `specFile` 时默认是模型文件所在目录 |
| `name` | string | 模型名（文件名前缀），只在第一次直接给规格时用，默认取 `title`；视图文件自动加后缀，用 `specFile` 时不用给 |
| `overwrite` | boolean | 默认 `false`，见“覆盖规则” |

返回每个视图的文件路径、节点/流向数、`metrics`（`crossings` 交叉数、`edgesThroughNodes` 穿过节点的线、`labelOverlaps` 重叠标签）、`readable`（是否清晰及原因）；偏密时返回 `suggestedViews`（可以直接当参数用）。

### `export_info_flow_html`

出交互版：一个 HTML 文件，里面有全图、总图、各分图和 N² 矩阵（都是本服务排好的 SVG），可以直接发给别人用浏览器打开，不联网、不引用外部脚本和字体（带 CSP，网页本身也连不了网）。

- 拖动平移、滚轮缩放、“适合窗口”；点方块高亮它的上下游和连线，右边列出流入、流出（点对端跳过去）；总图里点分组看它的对外流向
- 搜节点（`/`），按流向类型筛选，待确认清单（点一条跳到对应节点）
- 选起点和终点，在全图上高亮最短的流向链；鼠标停在线上看“谁 → 谁：内容（类型）”
- 大型项目照样有全图：静态全图看不清，交互版里可以缩放、只看一个节点或一条链路

参数同 `render_info_flow` 的模型参数和 `outputDir`、`name`、`overwrite`。`view: "suggested"` 时自动生成，不用单独调用。

### `render_info_flow_matrix`

| 参数 | 说明 |
|---|---|
| `level` | `node` 逐个节点（默认），`group` 分组之间 |
| `outputDir`、`name`、`overwrite` | 同上 |

返回文件路径、矩阵大小、有内容的格子数，以及没有输入、没有输出、孤立的节点。

## 模型

```json
{
  "title": "PCU 软件总体信息流（示例）",
  "source": "任务书 4.3～4.7；1553B ICD 表 2～5",
  "direction": "LR",
  "order": "auto",
  "groups": [
    { "id": "obc", "label": "星务计算机（BC）", "nodes": [
      { "id": "n1", "label": "遥测请求", "note": "子地址 1，500 ms" },
      { "id": "n2", "label": "间接指令", "note": "子地址 2，1 字" } ] },
    { "id": "app", "label": "应用软件", "nodes": [
      { "id": "n3", "label": "遥测组帧" },
      { "id": "n4", "label": "遥控指令处理" } ] }
  ],
  "flows": [
    { "from": "n1", "to": "n3", "label": "遥测请求", "kind": "command" },
    { "from": "n2", "to": "n4", "label": "指令码", "kind": "command" }
  ]
}
```

- `groups[].id`、`nodes[].id` 全图唯一（不能以 `G:` 或 `~` 开头，工具内部使用）；`flows[].from/to` 必须引用已定义节点。
- `note` 写周期、协议、方向或依据；含“待确认/待补充/待定/不确定”时节点画成琥珀色虚线，并列进 `.md` 的待确认清单。
- `kind`：`data` 蓝实线（数据流，默认）、`command` 橙粗线（控制流）、`event` 紫虚线（事件流）。也接受“数据流/指令/广播”等中文别名。
- `direction`：`LR` 分组从左到右排成列（默认），`TB` 从上到下排成行。
- `order`：`auto`（默认）自动排列泳道和泳道内的节点，交叉最少；`given` 按给出的顺序。
- 模型上限：24 个分组、300 个节点、800 条流向。一张图能看清的规模另见“可读性”。

## 视图

| 视图 | 画什么 | 布局 |
|---|---|---|
| 全图 | 全部节点和流向 | 一个分组一条泳道 |
| 总图 | 每个分组一个方块，内容写在方块里；同一对分组之间的全部流向合并成一条线，线宽表示条数，双向时两头都有箭头。线超过 15 条时只画流向较多的分组对，省略的在图例里写明，全部见 N² 矩阵 | 按流向分层（来源在左、去向在右），不画泳道 |
| 分图 | 一个分组的全部节点，加上和它直接相连的外部节点（灰色虚线框），只画碰到这个分组的流向 | 一个分组一条泳道，这个分组尽量居中 |
| 链路图 | 从起点沿流向走到的节点；给了终点时只取最短路径（有反馈环时“所有路径”会把半个系统带进来） | 一列一步：起点、第 1 步、第 2 步……；节点左上角标所属分组 |
| N² 接口矩阵 | 对角线是节点（或分组），第 i 行第 j 列写从 i 流向 j 的内容；标出无输入、无输出、孤立 | 矩阵，没有连线 |

## 布局方法

分层图（Sugiyama）方法，确定性（同一输入每次输出完全相同）：

1. **泳道排序**：`auto` 时把联系多的分组排在一起，尽量少跨泳道，同时尽量保持原来的顺序。
2. **长连线走通道**：跨越多条泳道的连线，在中间每条泳道里预留一个通道，和节点一起排队；连线在泳道之间走曲线、在泳道内部沿通道直线穿过，**不会压到节点**。
3. **交叉最少的顺序**：泳道内节点和通道的先后用重心法加相邻交换反复调整；同一泳道内有流向的两个节点尽量排在一起。
4. **同泳道的流向**：两端相邻时在两个节点之间直接连；不相邻时从节点侧面出来，沿泳道内侧边距走，选连出去的线少的一侧。
5. **纵向位置**：每个元素尽量对齐相连的元素（线平直），同时向上紧凑（不留大片空白）；用保序最小二乘（PAV）求解。
6. **端口和标签**：同一节点同一侧的多条线分开端口，按另一端位置排序；标签避开节点、表头和其他标签，长连线的标签放在它的通道里；泳道间隔按标签宽度加宽。

## 可读性

每张图都量出：

- `crossings`：连线交叉处数（同一节点出发或到达的线在节点旁边相碰不算）；
- `edgesThroughNodes`：经过了别的节点框的线条数（目标是 0）；
- `labelOverlaps`：压住节点或互相重叠的标签数。

一张图超过以下任一条时判为“偏密”，提醒并给出拆分建议：节点超过 30 个，流向超过 45 条，交叉超过 max(8, 0.9 × 流向数) 处，或有线穿过节点。**这些阈值是经验值**（用 PCU 示例和一个 50 节点的虚构模型的实际出图效果定的），不是标准。

实测（同一套指标）：

| 模型 | 1.0.0 | 1.1.0 全图 |
|---|---|---|
| PCU 示例（21 节点、29 流向） | 交叉 53 处 | 交叉 17～18 处，穿过节点 0 条 |
| 虚构大型模型（50 节点、98 流向） | 交叉 843 处，穿过节点 44 条 | 交叉 478 处，穿过节点 0 条，判为偏密并建议拆分 |

大型模型拆成视图后：总图 9 个方块、14 条线、交叉 9 处；“遥控上行 → 继电器”链路图 10 个节点、交叉 0 处。

## 覆盖规则

- **模型文件** `<名称>.flow.json` 是源头：已存在且内容不同时不覆盖，要先问用户，同意后再传 `overwrite: true`（建议先提交 Git 留住旧版）。内容相同不重写。
- **生成的 `.md` / `.svg`** 带生成标记（`info-flow-diagram:generated`），重新出图时直接更新，不需要 `overwrite`。
- **同名但不是本服务生成的文件**（手写的）不覆盖，除非 `overwrite: true`。
- 只在工作区里读写，路径越出工作区时报错；不删除文件。

## 文件

```
diagrams/
  <名称>.flow.json          模型（权威来源）
  <名称>.md / .svg          全图
  <名称>-总图.md / .svg
  <名称>-分图-<分组>.md / .svg
  <名称>-链路-<起点>-到-<终点>.md / .svg（或 -下游 / -上游 / -上下游）
  <名称>-N2.md / .svg       N² 接口矩阵（-N2-分组 为分组之间）
```

`.md` 在 VS Code、内网 Git 网页上能直接看到图片；里面折叠的 Mermaid 源码可以在支持 Mermaid 的编辑器里查看。不要手改 `.md` 和 `.svg`，改模型后重新出图。

## 图形约定

- 每个分组一条泳道，标题用分组色；节点白底、分组色边框。
- 节点名称和 note 自动换行；note 字号较小。
- 图例说明用到的流向类型、待确认、外部节点、链路起点、合并线宽和省略说明。
- 连线下面垫一层白色描边，交叉处看得出谁在上面。
- 布局、避让、颜色、图例是本服务自己的图形约定，不是国军标或行业标准的强制图形规范。

## 依据

- Mermaid 流程图语法：<https://mermaid.js.org/syntax/flowchart.html>（按离线语法约定生成，不联网）。
- 分层图布局：Sugiyama 等提出的分层有向图画法（分层、插入通道点、重心法减少交叉、坐标分配），按本服务的泳道场景做了简化。
- N² 图：系统工程中常用的接口分析方法（对角线是要素，非对角格是要素之间的接口）。
- 文档内容的依据由 `source` 和节点的 `note` 记录；图本身不能替代任务书、需求规格说明或 ICD。

## 局限

- **不解析文档。** 读 .docx/.xlsx/.pdf 由工作台的文档读取服务负责；本服务只接收结构化模型。
- **不是全局最优布线。** 交叉最少是启发式结果，不保证最少；稠密的系统靠拆视图解决，不靠一张图。
- **总图省略少量流向。** 线多时只画主要连接，完整清单在 N² 矩阵和模型里。
- **中文字体**：SVG 使用系统字体（微软雅黑/苹方/思源黑体），换行宽度是估算值；特别长的英文缩写可能提前换行。
- **Mermaid 源码**只是附带的文本表示，它的自动布局和 SVG 不同；以 SVG 为准。
- SVG 是静态图片，不支持点击、缩放交互。
- 只在工作区内读写；不删除文件；不联网；不调用外部命令。
