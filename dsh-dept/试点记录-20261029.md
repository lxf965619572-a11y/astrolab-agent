# DSH 官方桌面端试点记录（2026-10-28～29）

目的：判断部门工作流能否做成 DSH 插件、跑在 DeepSeek 官方桌面端上，从而不再维护 AstroLab 里与 DSH 重复的通用界面。

- 桌面端：DeepSeek Harness 0.2.1-rc.3（nightly 渠道，杭州深度求索签名，构建 be72761），装在 `D:\Programs\DeepSeek Harness`
- 源码：`deepseek-ai/deepseek-harness`，读的是 0.2.2-alpha.2 和 `dsh-v0.2.1-rc.3` 标签
- 试点数据目录：`runtime\desktop-trial\home`（`start-desktop-trial.cmd` 设 `DSH_HOME`），不动个人的 `~/.dsh`
- 部门组合包：`dsh-dept/`（`@astrolab/dsh-dept`，链接安装进试点 profile）
- 模型：云端 deepseek-flash，只用样例和公开内容

## 1 结论

**部门工作流可以做成 DSH 插件，但现在不迁移。**组合包已经把内网开关、精简、读取围栏、部门约定、部门模型、工具服务和 Git 防护都放进了官方桌面端，工作量约一天。挡住迁移的是三件 DSH 本身的事：

1. **审核面板做不了**：插件要提供主机接口（Remote API），只能在 DSH 仓库里用它的生成器构建（生成器先分析全部约 300 个包）。试点改用 Git 钩子（智能体不能提交，人用自己的 Git 工具审核提交），没有 AstroLab 那样的审核界面。
2. **版本和渠道**：装的是 nightly 预发布版，会自动检查更新、读取强制更新策略，这两项补丁关不掉（离线时不阻塞，见 3.4）。
3. **默认上传数据的地方多**（见第 3 节）：每一处都要靠组合包关，DSH 升级后要逐项复查。

建议：AstroLab 继续作为部门主用工具；`dsh-dept` 作为并行维护的组合包，与 AstroLab 共用读取围栏、Git 钩子、技能和工具服务。等 DSH 出稳定版、支持树外插件提供主机接口后再评估迁移，届时先让几位工程师在样例工程上试用。

## 3 安全发现

1. **产品埋点**（`product-analytics`、`desktop-product-telemetry`）：桌面端默认开，界面没有开关。发设备号、用户号、硬件信息（不含提示词和回复）。组合包关掉；启动脚本把导出地址指向本机死端口，第一次启动就不发。
2. **会话遥测**（`session-telemetry-otel`）：默认 `FEEDBACK_ONLY`——用户点赞、点踩、评分、写备注时，把截至那时的会话记录（含上下文：提示词、读到的文件、回复）上传到 `dsh-otel-collector.deepseeksvc.com`。组合包设 `mode: DISABLED`，并关掉反馈按钮；启动脚本设 `DSH_TELEMETRY_MODE=DISABLED`。
3. **官方 API 的会话日志附带上传**（`session-log-deepseek`）：默认开。用官方 DeepSeek 路由时，每次请求附带 `dsh_session_log` 字段，把会话的完整事件记录（含工具结果，也就是读到的文件内容，每次最多 8 MiB）一并上传。**试点第 1 轮真的上传了 5 次**（内容只是工具清单和被拒绝的读取，不敏感）。原因：启动脚本传了 `DEEPSEEK_API_KEY`，桌面端又把默认模型存成了官方路由。组合包关掉官方路由（`llm-deepseek`、`llm-deepseek-account`）并设 `enabled: false`；启动脚本只传部门的 Key。AstroLab 用 dept-llm 路由，查了它的 10 个会话，没有发生过；AstroLab 引擎也补上了这两项开关作双保险。
4. **更新和强制更新策略**：自动检查 `download.deepseek.com`，并从 `harness.deepseek.com` 读取强制更新策略；策略写在签名的应用清单里，补丁和环境变量都改不了。读了源码：请求失败时保持“不阻塞”，所以离线机器上不会被锁住；在联网的机器上会照常检查（只带平台、版本、渠道、语言）。
5. **DSH NEXT（第三方 anywhere-labs 的实验版）污染了个人 profile**：两个桌面端共用 `~/.dsh/profiles/desktop`，NEXT 留下了它的远程控制桥和“受信主机”列表（含公网 IP 119.80.252.59）。已清理，原文件备份在 `~/.dsh/profiles/desktop/_backup-dsh-next-20261029-030339`。`~/.agents-anywhere` 未动。
6. **个人桌面端（`~/.dsh`）已关掉上面 1～3 项**（10-29）：在 `profiles/desktop` 和 `profiles/web` 的用户层末尾加了四条（`product-analytics`、`desktop-product-telemetry` 关，`session-telemetry-otel` 设 `DISABLED`，`session-log-deepseek` 设 `enabled: false`），原文件备份为同目录的 `cordis.patch.yml.bak-20261029-privacy`。其余不动：四个官方预设、官方模型路由、联网搜索、反馈按钮都照旧。没放进 `~/.dsh/cordis.patch.yml`（对所有 profile 生效的那层）：命令行的 sdk、headless profile 没有埋点插件，每次启动都会报 “entry not found”。

## 4 工程发现（做组合包时踩到的）

- **按 id 打补丁会替换整个 config**（`dsh --dump-config` 验证）。预设不能只去掉几个工具，只能照抄官方 `standard` 预设、去掉不要的，再关掉官方四个预设。**每次升级 DSH 都要对照新版 standard 更新部门预设。**
- **只留一个部门预设的影响**（读了 rc.3 源码）：
  - 官方四个预设：standard（默认编码智能体）、ptc（工具改成写程序调用，多一个 run_code）、minimal（只有常驻命令行和文件读写）、cordis（“创作者”，写 DSH 插件用，带 tool-cordis 和插件市场）。部门预设是 standard 减去联网、定时、目标、计划模式、脚本编排、插件管理。
  - 界面上没有模式切换；插件管理页“添加插件”菜单里的“创建你的插件”变成灰的、写着缺少创作者预设（不会报错）。
  - **会话记着自己的预设，重新打开时按记的去找**（`session-controller` 的 `resume` → `agent-preset-registry.resolve`），找不到就报 “Unknown agent preset”。所以：部门预设的 id `dept` 以后不能改名；个人 `~/.dsh` 里在 standard 下建的会话不能挪到部门 profile 里打开。试点的 4 个会话最后都是 `dept`（有一个先记了 standard、第一轮前切成 dept）。
  - 子智能体沿用父会话的预设，也是 dept。
- **用户层（profile 自己的 `cordis.patch.yml`）盖过组合包的配置**，桌面端会往里写（例如默认模型）。但**组合包关掉的插件，用户层不会重新打开**。所以部门必须强制的东西只能用“关插件”，不能靠默认配置；部署时由安装程序写好用户层的初始值（试点里手工把默认模型改成了 dept-llm）。
- **账号平台不能关**：关掉 `deepseek-account` 等后桌面端启动失败（“desktop welcome: Web request failed”）。没有官方模型路由时它只用于启动页。
- **组合包声明 DSH 版本**（`engines.dsh`），版本不符时 DSH 拒绝加载——升级 DSH 必须同时更新组合包，这是好事。
- **网页版的工具挂在预设里，不在全局**：AstroLab 用的 sdk 模式是全局挂载，所以同一个“精简”在两边写法不同。
- **桌面端切换工作区不直观**：两次测试都留在默认工作区 `Documents\deepseek-harness\default-workspace`。AstroLab 的项目列表更适合部门用户。
- **插件管理页还开着**（`ui-plugin-manager`）：用户可能在那里关掉部门组合包或重开被关的插件，正式使用前要关掉它并验证。

## 5 没有做完的

1. 桌面端上 Git 防护的实装：在 Git 仓库工作区里新建会话，让智能体提交，应被钩子拒绝（一分钟的事，需要先在桌面端把工作区切到 `runtime\app-data\workspace\sample`）。
2. 离线验证：断网（或防火墙禁止桌面端出站）后启动并完成一个任务，确认不卡在更新或启动页。
3. 关掉插件管理页后，确认用户不能关部门组合包。
4. 安装形态：组合包打成 tgz 离线安装，安装程序写用户层初始值。
