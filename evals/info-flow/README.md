# 信息流梳理 Skill 评估

检验 `skills/info-flow`（信息流梳理）和内置服务 `mcp/infoflow`：智能体读任务书和 ICD，建信息流模型，出全图、总图、链路图和 N² 矩阵，列出依据和待确认问题。换模型（DeepSeek V4 / 局域网 Qwen）、改技能、升级 DSH 前后各跑一遍，用 `summary.json` 里的数比较。

| 文件 | 说明 |
|---|---|
| `pcu/case.mjs` | 用例 pcu 的输入、提示词和答案（节点类别、主链、冲突、加分项），**不要给智能体看** |
| `pcu/答案表.md` | 同一份答案的人读版：提问怎么答、必须做对的、人工核对项、评分方法 |
| `prepare.mjs` | 准备示例工程：上一次的 `diagrams/` 移到 `results/`，输入恢复原样，记下工作区现状 |
| `score.mjs` | 评分：读工作区产出和任务记录，结果写到 `results/<时间>-<用例>[-<标签>]/` |
| `lib.mjs` | 公用函数：找任务记录、解析会话日志、模型分析（用 `mcp/infoflow` 重算视图和指标） |

评测代码和答案都在 `evals\` 下，读取围栏挡着，智能体读不到。

**用例 pcu 偏乐观**：技能的参考资料 `references/pcu-example.md` 就是用这两份材料写的示例模型，智能体第一次使用时会读它。pcu 能可靠衡量的是过程（读了文档、先校验、换视图用 specFile、不生成 Word、不擅自定值、不手改生成文件）和汇报；内容分衡量的是“照着示例能不能做对”。要比较不同模型自己梳理的能力，得再做一份技能里没有的用例（换一个单机、换一套冲突），放在 `evals/info-flow/<用例>/`，写一份 `case.mjs` 即可，`prepare`/`score` 不用改。

## 步骤

1. 准备（示例工程的位置自动找，开头会打印；要指定用 `ASTROLAB_SAMPLE=<目录>`）：

   ```text
   node evals\info-flow\prepare.mjs
   ```

2. 在 AstroLab 中打开“示例工程”，选**信息流梳理**技能，新建任务，输入 prepare 打印的提示词：

   ```text
   根据 docs 下的《PCU软件研制任务书-示例2.docx》和《PCU-1553B接口控制文件-示例2.xlsx》，梳理 PCU 应用软件的信息流：出全图、总图、“间接指令 → 负载继电器”的链路图和 N² 接口矩阵，列出依据和待确认问题。
   ```

3. 智能体提问时按 `pcu\答案表.md` 第 0 节回答。
4. 完成后评分（`--label` 写模型名，方便对比）：

   ```text
   node evals\info-flow\score.mjs pcu --label qwen3.8-27b
   ```

   默认取 prepare 之后示例工程里最近一个信息流任务；指定任务用 `--task <任务 id>`（工作台“历史”里的任务、或数据目录 `projects\<示例工程>\tasks\` 下的文件名）。
5. 看 `results\<时间>-pcu-<标签>\summary.md`：第四部分摘出的原文逐条看一眼；按答案表第 3 节人工核对编造和画反的流向。写评估记录 `评估记录-pcu-<模型>-<日期>.md`：环境、模型、用时、用量、客观项、加分、人工核对、发现的技能问题。

每次评测之间都新建任务，并重新运行 `prepare.mjs`。

## 评分内容

| 部分 | 怎么判断 |
|---|---|
| 一 过程 | 任务记录（`<数据目录>\logs\<任务 id>.jsonl`）里的工具调用：选了技能、两份输入都读了、出图前先 `validate_info_flow`、出了 N² 矩阵、之后换视图用 `specFile`、没有 docgen 和新 .docx、shell 里没有联网命令、`overwrite: true` 之前有提问、没有用 write/edit 改生成的 .svg/.md、输入文件和仓库种子的 SHA-1 相同 |
| 二 产出 | `diagrams\` 下这次新写的 `.flow.json`；用 `mcp/infoflow` 的同一套代码校验、按模型重新生成全图和总图，SVG 要和磁盘上的完全相同（不同说明手改过或改模型后没重出）；全图按模型重算可读性 |
| 三 模型 | 节点按名字（对不上再看 note）归类，检查泳道、主链（相邻两类 3 步内有通路）、参数写 MRAM、EEPROM 没有流入、3 处冲突在模型里标【待确认】且写出两个值（只写一个值记“擅自定值”）、遥测字没逐个画、节点数、note 写依据、流向标签和类型 |
| 四 汇报 | 最后一次出图之后助手写的文字，加上 diagrams 里这次新写的说明 .md：每个冲突要在同一行出现两个值（或全部关键词），出处两处以上记“带两处出处”；有经过存储的环时要解释；N² 矩阵里无输入/无输出的节点 80% 以上被提到 |
| 五 记录 | 模型、用时、步数、工具调用、提问、token 用量；和技能示例模型的同名节点、同名流向数 |

**结果作废**：任务记录里出现读 `evals\info-flow`、`tests\pcu-demo`、`expected-output` 的调用。

客观项是“通过数 / 适用数”，加分单独计。第四部分是关键词判断，宁可多报让人看，不当作最终结论。

## 说明

- 只看示例工程的任务记录（项目上下文第 5 条）。
- `score.mjs` 不联网、不启动子进程，在麒麟上用同一条命令（路径分隔符随系统）。
- 节点归类的正则写在 `case.mjs` 里。某次判错了（例如模型把“遥测组帧”叫“遥测数据打包”没对上），`summary.md` 的说明列里会写出匹配到的节点名：确认是模型没问题的话，补正则，不要改模型去迁就脚本。
- 试跑：11-05 的一次任务（plugin 1.2.0、deepseek-flash、同时选了汇报绘图）客观项 44/45，唯一不通过的是当时的全图交叉 22 处（评分规则改为工具判“清晰”后通过）；用示例模型改出擅自定值、写 EEPROM、逐个画遥测字、断一条主链、手改 SVG 的反例，这些都判为不通过。
