# 信息流评测答案表：pcu（不要给智能体看）

输入：示例工程 `docs/PCU软件研制任务书-示例2.docx`、`docs/PCU-1553B接口控制文件-示例2.xlsx`，两份都是虚构演示材料。下面的条款号按任务书的章节号（4.3.1 遥测、4.3.2 遥控、4.3.3 时间同步、4.3.4 方式码、4.3.5 广播、4.4 加断电、5 性能要求、6.1 1553B 接口、7 可靠性与安全性），ICD 表 1～5 依次是总线参数、子地址、方式码、遥测字、指令码。

**注意**：技能的参考资料 `skills/info-flow/references/pcu-example.md` 用的就是这两份材料，技能第 11 步之前智能体通常会读它。所以本用例的内容分偏乐观，它衡量的是“过程守规矩、照着示例能做对”；要看模型自己从文档里梳理的能力，需要一份技能里没有的用例。

## 2 必须做对

- 泳道：星务计算机（BC）、1553B 总线、应用软件（可拆成几组）、采集电路、执行机构、数据存储。
- 主链：遥测请求 → 1553B → 遥测组帧 → 遥测消息；间接指令 → 遥控指令处理 → OC 指令 → 负载继电器；采集电路 → 数据采集调度 → 遥测组帧 / 充电控制 / 过放保护。
- 存储：运行参数（过放门限、充电档位）写 MRAM 三份、三取二（任务书 7）；EEPROM 只提供固化的默认参数，不能有写入 EEPROM 的流向。遥测每 1 s 一帧存 MRAM（任务书 4.6）。
- “遥测组帧 ↔ MRAM”这类读写闭环保留，汇报里解释为正常读写，不为消除提醒改箭头。
- 粒度：ICD 表 4 的 40 个遥测字只画成“遥测数据/遥测帧”一类；节点按功能、接口合并。
- 依据：节点 note 写章节或表号；模型 `source` 写两份文件。
- 产出：`diagrams/` 下 `.flow.json`、全图、总图、“间接指令 → 负载继电器”链路图、N² 矩阵；不生成 Word；不改 `docs/` 下的文件；不手改生成的 `.md`/`.svg`。
- 汇报：N² 矩阵里无输入/无输出的节点逐个说明（外部来源、终端执行机构、存储属于正常）。

## 3 人工核对（脚本判断不了）

- **编造的流向**：文档里找不到依据的流向。常见的有：PCU 主动向星务计算机发数据（1553B 里 RT 只能应答 BC，遥测是 BC 来取）；EEPROM 被写入；采集电路直接连到遥测帧（应经过采集调度）；看门狗、EDAC 画成和 BC 的接口。
- **方向画反**：例如“遥测组帧 → 遥测请求”、“继电器 → OC 指令”。
- 待确认的两处出处是否引对（章节号、表号）。
- 汇报里说“推断”的内容，是否先问过用户。

## 5 评分方法

`node evals/info-flow/score.mjs` 自动判断第 1、2 节和第 4 节的大部分，结果在 `summary.md`：

- **客观项**：通过数 / 适用数。第四部分（汇报）是关键词判断，摘出的原文行要人工看一遍。
- **加分**：单独计数，不进客观项。
- **结果作废**：任务记录里出现读本答案表、`skills/info-flow/tests/pcu-demo`、`expected-output` 的调用。
- **偏乐观**：读了 `references/pcu-example.md`，或模型和示例同名节点超过 70%。
- 第 3 节人工核对的结果写进评估记录，不改客观项的数。
