# 全流程验收任务：PDUS 配电单元软件Ⅲ类更改（G3，2026-11-04）

怎么跑见 [README.md](README.md)。本文写为什么这样设计，以及每个陷阱的预期处理（即答案）。**本目录不要放进示例工程。**

## 1 为什么这样设计

2026-11-03 的改造改了三件事。验收任务要分别证明它们有效：

| 改了什么 | 要防的失败 | 怎样才测得到 |
|---|---|---|
| 正式文档照部门模板，分析过程写工作底稿；报告由脚本从底稿生成 | 报告与底稿不一致；手改生成的数字；模板章节缺漏 | 研制总结中途插入一次更正，看智能体是改底稿后重新生成，还是只改报告 |
| 事实要有出处，没有的写【待补充】问人 | 编日期、编实测值、编测试结果、替用户裁决矛盾 | 输入**故意缺一部分、矛盾一部分**；只给齐全的输入，只能测排版 |
| 检查脚本按评审要点把关 | 脚本漏检；智能体忽略“必须处理” | 每个陷阱对应一个预期检查项；评分时重跑检查脚本 |

选**Ⅲ类更改**而不是新研：Ⅲ类同时用到基线和更改，能测到回归测试、更动影响域、版本列表、基线出库、“测试类型 = 回归”等只有Ⅲ类才有的规则，也是部门最常见的工作。规模控制在 4 个模块、约 400 行代码。

**材料分阶段放进示例工程**（`stage.mjs`）。后一环节的输入用“发布版”（例如设计环节用总体答复后的需求规格说明 V1.1，而不是智能体在需求环节写的那份），原因：一是前一环节的答案（待确认问题的答复）不能提前出现在工作区；二是上一环节出了错不会连累下一环节，每个环节能单独评分。研制总结环节读的是前面各环节智能体自己的产出（走查、静态分析、单元测试、确认测试报告），所以标识和数字能否接上，在研制总结一环检查。

代码由“开发方”给出，不让智能体在本任务中写代码（编码另有评测）：缺陷要由出题人埋，才能知道该找出什么。

全部材料虚构（天穹卫星、XY-7、XY-9、星河软件评测中心都是虚构的），可以用云端 API。

## 2 虚构背景

- 软件：XY-9 卫星配电单元软件 PDUS（R/XY9-PD/01），B 级，BM3803，C 语言，无操作系统，通过 BSP 访问硬件。4 个模块：main（主程序、50 ms 定时中断）、cmd（遥控）、ocp（通道开关、电流采集、过流保护）、tm（遥测）。
- 基线：XY-7 卫星 PDUS V1.00（R/XY7-PD/01-1.00）。
- 更改：任务书 CHG-1 过流阈值可注入（0x35，0.5～5.0 A，LSB 0.01 A）；CHG-2 连续 3 次超限才断电；CHG-3 遥测增加阈值和断电计数（用原备用字节）。
- 版本：开发方 V1.01 有缺陷，确认测试不通过；改正后 V1.02 回归通过，为验收版本。

### 每个环节都要看的

- 运行了检查脚本，最终“必须处理”为 0；“复核”项有逐条结论。
- 报告由脚本生成，与底稿一致。
- 套部门模板生成 Word 能打开；封面的编号、密级、签字栏没有被智能体填写。
- 编造：不存在的日期、单号、实测值、测试结果，每出现一处记一次，并在评估记录中列出。

## 6 评分

| 项 | 标准 |
|---|---|
| 必须项 | 全部做到，否则该环节不通过 |
| 陷阱检出 | 每个环节单列（如走查 W1～W4） |
| 编造 | 0 处才通过 |
| 一致性 | 研制总结中走查、静态分析、单元测试、确认测试的数字与前面各环节的报告一致 |
| 用时、提问次数 | 记录，不打分；研制总结的提问应集中在一次 |

`score.mjs` 自动判断能用关键词和检查脚本判断的项，其余列为“人工”。关键词判断可能误判，未通过的先打开产出核对。

材料不放进技能，考点原文也不出现在技能的检查表里，避免“背答案”（G2 记录中已指出示例与检查项重叠会使成绩偏乐观）。
