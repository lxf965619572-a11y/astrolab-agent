- 时间：2026-10-25
- 环境：Windows 笔记本，DSH 0.2.1-rc.2，DeepSeek 官方 API（deepseek-flash）
- 会话：`session-d9d98661`，新建会话，一轮完成，约 8.9 分钟，70 余次工具调用（其中生成 Word 6 次）
- 用量：约 770 万 token，其中缓存命中 749 万，未缓存输入约 11.2 万，输出约 9.6 万
- 输入：上一次评估生成的《概要设计说明-TCUS-20261025》，加上 SRS、硬件接口说明、通信协议
- 用户输入：“根据概要设计报告，输出详细设计报告，比如 htr_out 模块”
- 输出：`详细设计说明-htr_out-20261025.md`（58 KB）、`.docx`（流程图 8 幅：状态图 1 幅、函数流程图 7 幅）、`待确认问题清单-htr_out-20261025.xlsx`
- 检查脚本：第一次 0 项必须处理、9 项复核（数值出处），在设计决策 D-003、D-013 中补充出处后 0 项

这次没有答案表，评估的是两个 Skill 能不能衔接：详细设计是否以概要设计为依据，是否与它一致，能不能发现概要设计的问题。

## 1 衔接情况

| 检查项 | 结果 |
|---|---|
| 对外接口 | 8 个对外函数的原型、调用者、执行环境、返回码与概要设计 7.2.12 完全一致；内部函数 3 个（唯一写出口 htr_out_commit、编号检查、位计数） |
| 模块关系约束 | 遵守概要设计 5.3“htr_out 不调用 cmd_exec 与 auto_ctrl”；工作模式由本模块保存 |

| 编号冲突 | 概要设计和详细设计都用 D-xxx、Q-xxx。它改用“HLD-4 决策 006”“HLD-12 第 8 项”引用概要设计的条目，避免混淆 |
| 概要设计的暂定方案 | 按概要设计的暂定方案实现（超过 8 路拒绝、模式切换保持输出），并在本文的 Q-001、Q-004 中注明对应关系 |

## 2 发现的概要设计问题

详细设计指出了 4 处概要设计的问题，其中 Q-002、Q-003 是概要设计本身的接口缺漏：

| 编号 | 问题 | 评价 |
|---|---|---|
| Q-002 | 概要设计 10 章要求写后读回不一致时“置故障标志并按安全方向全部断开”，但 7.2.12 的返回码中没有“写失败” | 真实的接口缺漏 |
| Q-003 | 概要设计要求 htr_out“置故障标志”，但 5.3 的模块关系和 7.2.12 的“使用的接口”中没有 htr_out 到 stat_mgr 的调用；故障标志的位分配也没有 | 真实的接口缺漏；概要设计的检查表已据此补充 |
| Q-006 | 初始化流程中没有 stat_init 的位置，初始化期间置的故障标志可能被随后的 stat_init 清零 | 真实的缺漏 |
| Q-005 | 重复接通已接通的一路时是否计入上限、返回什么 | 合理 |

## 3 问题

| 问题 | 位置 | 说明 |
|---|---|---|
| 初始化失败分支没有显式断开 | 6.1 htr_out_init 步骤 4 | 写 HTR_OUT = 0 后读回不为 0 时，写“不写 HTR_EN（保持复位值 0）”。但同一节后面又分析了“软件单独复位而 FPGA 未复位时 HTR_EN 可能仍为 1”：这种情况下失败分支会让输出保持使能、HTR_OUT 内容未知。应在失败分支显式写 HTR_EN = 0 |
| 读回不一致后不写 HTR_EN = 0 | D-008、6.9 | 以概要设计决策 006“不做 HTR_EN 的切换”为理由，但该决策针对的是正常输出变更；读回不一致时 HTR_EN = 0 是硬件保证的断开（HW-5.2）。D-008 自己也写了“输出可能仍保持接通”。已列入 Q-003，但建议方向应反过来 |
| 读回不一致时暂按返回 0（成功） | 6.2、6.3、6.5 | 调用者会按成功计数，掩盖了故障。已列为 Q-002，但暂定方案不合适 |
| 照抄了概要设计的错误 | 3.2 的 HLD-9 | 概要设计的栈估算写“加 1 层中断嵌套”，与其自身的 D-004（不嵌套）矛盾，详细设计照抄，没有核对 |
| 读了评测目录和其他模块的设计 | 过程 | 读了 `evals\detailed-design\oc_ctrl\reference\` 下的参考详细设计、`sample\design\oc_ctrl\doc` 下 oc_ctrl 的设计作为格式样例，还读了 check-design.mjs 和 flowchart.mjs 的源码。参考设计是另一个模块的，不影响这次的内容，但评测目录不应被读取 |
| 生成 Word 6 次 | 过程 | 每次改流程图都重新生成，token 用量是概要设计的 2 倍多（缓存命中高） |

## 4 结论

两个 Skill 能够衔接：详细设计以概要设计为依据，接口、执行环境、时间预算、共享数据保护和暂定方案都一致，并且发现了概要设计自身的 3 处接口缺漏。主要问题在故障路径的安全设计：初始化失败分支和读回不一致时都没有用 HTR_EN = 0 这一硬件保证的断开方式，读回不一致时返回“成功”。

## 5 据此对 Skill 的修改

| 修改 | 位置 |
|---|---|
| 初始化自检失败的分支要显式把输出置于安全状态，不依赖复位值 | detailed-design：design-checklist.md 第 1 节 |
| 新增“与概要设计的衔接”检查：返回值是否覆盖全部结果、要调用的其他模块接口概要设计中有没有、引用的条款与其他文件是否一致 | detailed-design：design-checklist.md 第 1A 节 |
| 只读输入文件和本 Skill 的参考文件，不读评测目录、其他模块的设计；检查脚本不读源码 | detailed-design、preliminary-design：SKILL.md 约束 |
| 模块关系和“使用的接口”要包括故障上报、计数等跨模块调用；对外接口的返回值要覆盖第 10 章规定的故障情况 | preliminary-design：architecture-checklist.md 第 1 节 |

说明：detailed-design 检查表新增的第 1A 节是通用的检查项，以后重测 oc_ctrl 时会对“概要设计与 SRS 的矛盾”（答案表 F1、F2、F4）有一定提示作用，评分时要考虑。
