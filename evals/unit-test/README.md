# 单元测试 Skill 评估

用埋了缺陷的虚构模块，衡量 unit-test-design Skill 产出的测试“能不能发现问题”，而不只是“覆盖率高不高”。

| 用例 | 模块 | 考察重点 | 缺陷 | 变异体 |
|---|---|---|---|---|
| `cmd_check` | 遥控指令帧合法性检查 | 等价类、边界值、MC/DC、检查优先级、计数回绕和饱和 | 6 | 22 |
| `uart_drv` | RS-422 串口收发驱动 | 寄存器访问替换、写入顺序、下层函数桩、超时和 tick 回绕、中断服务程序、环形缓冲、关中断配对 | 7 | 26 |

## 1 文件

每个用例一个目录（`cmd_check/`、`uart_drv/`），内容相同：

| 文件 | 说明 |
|---|---|
| `sample/utest/<用例>/` | 工作区中的被测模块：`src/` 是**埋了缺陷**的源码，`include/` 是头文件，`doc/` 是详细设计（预期结果的依据） |
| `<用例>/reference/` | 正确的参考版源码（**不要给智能体看**） |
| `<用例>/defects.json` | 埋入的缺陷，即参考版到工作区源码的差异 |
| `<用例>/mutants.json` | 变异体，用来衡量测试的检错能力 |
| `<用例>/reference-test/` | 人工按设计编写的参考测试，评分基线 |
| `score.mjs` | 评分脚本 |
| `build-sample.mjs` | 由参考版和缺陷重新生成工作区源码（源码被改坏时用来恢复）：`node evals\unit-test\build-sample.mjs <用例>` |

## 2 怎么测

1. 在 DSH 中**新建会话**（Skill 改动后不用重新运行 setup.ps1，但要新建会话）。会话要开在 `sample` 工作区中，下面的路径都相对于 `sample`。
2. 在新会话中输入（二选一）：

   ```
   对 utest\cmd_check 做单元测试。被测代码在 src，详细设计是 doc\cmd_check-详细设计.md，目标平台 BM3803，用手写驱动和桩，测试代码放在 utest\cmd_check\test，最后写单元测试报告。
   ```

   ```
   对 utest\uart_drv 做单元测试。被测代码在 src，头文件在 include，详细设计是 doc\uart_drv-详细设计.md，目标平台 BM3803，用手写驱动和桩，测试代码放在 utest\uart_drv\test，最后写单元测试报告。
   ```

3. 智能体完成后，在本工程目录评分：

   ```
   node evals\unit-test\score.mjs cmd_check
   node evals\unit-test\score.mjs uart_drv --run sample\.utest\uart_drv\last-run.json
   ```

   默认评 `sample\utest\<用例>\test`，评其他目录时把目录写在用例名后面。`--run` 指定智能体的运行记录，评分时沿用它用的宏定义和编译选项（智能体用了 `defines` 时必须加）。测试目录中含 `.h` 的子目录（如替换寄存器头文件的 `hw\`）会自动放在 `include` 之前。

   结果写在 `evals\unit-test\results\<时间>-<用例>-test\summary.md`。

4. 检查报告：

   ```
   node skills\unit-test-design\scripts\check-ut.mjs sample\utest\<用例>\test\单元测试报告-<用例>-<日期>.md --run sample\.utest\<用例>\last-run.json
   ```

   运行记录的目录名是智能体调用 `run_unit_tests` 时的 `name`（默认取被测文件名），以智能体回复中的“运行记录”为准。

5. 下次重测前，把 `sample\utest\<用例>\test` 改名或移走，并新建会话，否则智能体会在旧测试上修补。

## 3 评分指标

| 指标 | 怎么得出 | 期望 |
|---|---|---|
| 预期结果错误 | 测试在**正确的参考版**上失败的用例数 | 0。非 0 说明预期不是按设计推导的 |
| 埋入缺陷检出 | 逐个把缺陷放进参考版，有新的用例失败即检出 | 全部 |
| 变异得分 | 逐个应用变异体，出现新的失败、崩溃或超时即“杀死” | 越高越好 |
| 语句、分支覆盖 | 测试在参考版上的覆盖率 | 100% |
| 被测代码是否被修改 | 工作区源码与原始版本比较 | 否 |

评分用的是参考版源码，所以测试“碰巧适应了”工作区里的缺陷代码（照着代码写预期）时，会在参考版上失败，体现为“预期结果错误”，同时这个缺陷也检不出来。

测试在参考版上就崩溃或超时（例如没有替换寄存器访问），评分显示“无法评分”。

| 用例 | 参考测试基线 |
|---|---|
| cmd_check | 25 个用例，预期错误 0，缺陷 6/6，变异 22/22，语句 61/61，分支 50/50 |
| uart_drv | 31 个用例，预期错误 0，缺陷 7/7，变异 26/26，语句 86/86，分支 42/42 |

## 4 埋入的缺陷

### 4.1 cmd_check

| 编号 | 缺陷 | 应该发现它的用例 |
|---|---|---|
| D1 | 温度门限 1000 被判为非法（`>` 写成 `>=`） | 参数上边界 1000 |
| D2 | 安全模式禁止条件缺括号，载荷加电在所有模式下被拒绝 | 正常、维护模式下的载荷加电 |
| D3 | 错误计数回绕，应饱和在 255 | 错误计数 255 再加 1 |
| D4 | 长度检查只拒绝过短的帧 | 长度 9 |
| D5 | 程序上注使能在正常模式也被接受 | 正常模式下的程序上注使能 |
| D6 | 同步字只检查了第 1 个字节 | 只有第 2 个字节错误（MC/DC） |

### 4.2 uart_drv

| 编号 | 缺陷 | 应该发现它的用例 |
|---|---|---|
| D1 | 发送超时差一个 tick（`>=` 写成 `>`） | tick 桩：经过 5 tick 仍未就绪应超时 |
| D2 | tick 回绕时误判超时（起点加门限后比较） | 起点 0xFFFFFFFE，等待 1～2 tick 后就绪应成功 |
| D3 | 接收缓冲区满判断错误，第 33 个字节覆盖最早的数据 | 连续接收 33 个字节 |
| D4 | 只检查校验错，帧错的字节被存入缓冲区 | 只有 FE=1 的字节 |
| D5 | 缓冲区为空时提前返回，没有恢复中断 | irq 桩：空缓冲区读取，lock/unlock 次数相等 |
| D6 | 分频值截断取整 | 19200、38400、57600 的分频值（只测 9600、115200 发现不了） |
| D7 | 先使能收发再写分频值 | 寄存器写入记录：写 SCALER 时 CTRL 为 0（只看最终寄存器值发现不了） |

D1 和 D2 在同一行，工作区源码中合成为一行 `if (sys_ticks() > start + UART_TX_TIMEOUT_MS)`。

## 5 报告的人工检查要点

评分脚本只看测试代码。报告要另外检查：

### 5.1 共同要点

| 要点 | 正确做法 | 错误做法 |
|---|---|---|
| 失败用例 | 缺陷对应的失败用例全部列为疑似缺陷，预期保持按设计 | 把预期改成代码的实际输出；删掉失败的用例 |
| 检查脚本 | 运行 `check-ut.mjs`，“必须处理”为 0 | 没有运行，或运行后不改 |
| 设计已明确的规定 | 直接按设计判缺陷 | 又列成待确认问题，或建议修改设计迁就代码 |

### 5.2 cmd_check

| 要点 | 正确做法 | 错误做法 |
|---|---|---|
| 未定义的模式值 | 设计只规定了三种模式，没有规定 `mode` 为其他值（如 3）时怎么处理，应列为待确认问题 | 按代码行为断言“返回 CMD_OK” |
| static 函数 | `code_known`、`check_param` 通过 `cmd_check` 测试，或在驱动中 `#include` 被测 `.c` | 去掉被测代码中的 `static` |
| 编译警告 | `-Wparentheses` 警告（D2 所在行）写入疑似缺陷或复核意见 | 忽略 |
| MC/DC | 编译器不能测量时写分析表并用 `check_mcdc` 核对，报告写“未测量；分析表核对……” | 没测量却写“MC/DC 覆盖率 100%” |
| 主机局限 | 说明主机为小端、SPARC 为大端；本模块用移位组装字段，结果与字节序无关 | 不提 |

### 5.3 uart_drv

| 要点 | 正确做法 | 错误做法 |
|---|---|---|
| 寄存器访问 | 在 `test\hw\` 中写替换的 `uart_reg.h`，读写宏改为调用寄存器模型，`includeDirs` 中排在 `include` 之前；报告写明替换方式 | 修改 `include\uart_reg.h` 或被测代码；测试直接访问 0x80000100 导致崩溃后放弃 |
| 计数溢出（陷阱） | 设计只说 `rx_err`、`rx_ovf` 是 16 位，没有规定到 65535 后回绕还是饱和，应列为待确认问题 | 按代码行为断言回绕 |
| 不可达判断 | 工作区代码中“缓冲区满丢弃”一行（因 D3）只有第 34 个字节才能到达；能构造输入就补用例 | 写成“防御性代码不可达” |
| 主机局限 | 寄存器模型是按设计写的，与真实控制器的时序（TH 何时置位、写 1 清除的时机）可能不同；中断与 `uart_read` 的并发要在目标机验证 | 不提 |
| 桩 | `sys_ticks`、`irq_lock`/`irq_unlock` 写桩，桩只记录和返回，不复制业务逻辑 | 桩里实现超时判断等被测逻辑 |
